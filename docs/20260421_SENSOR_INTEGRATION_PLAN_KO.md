# 실내 사이클링 앱 — 센서 연동 통합 계획서 (단일 문서)

본 문서는 센서 연동 관련 논의를 **누락 없이 한 파일로 통합**한 것입니다.

**대외 정책:** 앱의 **인터페이스(도움말, 버튼, 타이틀, 에러 문구 등)는 영어**가 기준입니다. 본 계획서는 **한국어**로 작성합니다.

---

## 1. 배경·목표·제품 정체성

### 1.1 배경

- 앱은 **전 세계 사용자**를 대상으로 한 **Indoor Cycling Free** 버전으로 설계한다.
- **시작 동기:** 저항을 손으로 조절하는 **무센서 수동 실내자전거** 사용자의 **지루함 완화**.
- **인식:** 무센서만으로는 체감 개선에 한계가 있어, **저가 케이던스(등) 센서** 연동으로 재미를 높이려 한다.
- **확장:** 센서를 붙이는 김에 **스마트 트레이너**(Zwift 등에 쓰이는 장비) 사용자도 **같은 앱**으로 쓸 수 있게 하되, Free 범위에서는 **“데이터 입력 장치”로만** 다룬다.

### 1.2 목표(한 문장)

**Street View 기반 실내 주행**에서, **페달·휠 입력(센서/트레이너)**을 읽어 **가상 속도·주행 체감**을 자연스럽게 만든다. 서버·DB·AI 없이 **기기 내부**만 사용한다.

### 1.3 비목표(명시적으로 하지 않음)

- 클라우드 DB, 계정, 원격 동기화
- **AI** 기반 페이싱·예측·학습 모델
- **ERG·저항 자동 제어**, 코스별 자동 저항 변화(스마트 트레이너 제어)
- Zwift와의 **기능 경쟁**(동시 앱 두 개로 같은 트레이너 점유 등)

## 2. 제약·전제

| 항목 | 내용 |
|------|------|
| 처리 위치 | **앱 + 사용자 스마트폰**만 |
| 데이터 저장 | **로컬**(Preferences / localStorage 등). “전체 라이딩 로그”가 아니라 **요약 스칼라 + 짧은 버퍼** 위주 |
| 통계 기본 | **평균값**(예: 1분 테스트 구간의 **평균 RPM**). 필요 시 이후 **아주 얕은 절단 평균**은 구현 세부로만 검토(문구는 여전히 “average”) |
| 캘리브레이션 컨셉 | **질문 대신 “1분 측정”** 버튼. **최고 저항에서 1분 최대 노력** 후 **평균 RPM**을 개인 상한 앵커로 사용(“무리 없이”보다 기준이 명확함) |
| 언어 | **UI 전부 영어**(모달·토스트·About 한 줄 포함) |
| 코드 운영 | **코드 수정 작업이 있을 때마다** 작업 단위로 **`git commit`** 수행 |

## 3. 사용자·장비 범위

### 3.1 사용자 유형

1. **무센서** — 기존 슬라이더 속도만 사용(동작 유지).
2. **케이던스만**(예: CYCPLUS 등) — RPM 기반 effort.
3. **케이던스 + 속도(휠) 센서 동시** — 아래 **듀얼 결합 규칙** 적용.
4. **스마트 트레이너** — **읽기 전용**. **FTMS** 등에서 케이던스·(가능하면) **파워**만 수집. **저항 제어는 하지 않음**.

### 3.2 기술적으로 구분하는 입력 장치

| 구분 | 예시 | 전형적 BLE | Free에서의 역할 |
|------|------|------------|------------------|
| 단순 센서 | CYCPLUS 등 | **CSCP**(Cycling Speed and Cadence) | **Cadence**, 선택적 **Wheel speed** |
| 스마트 트레이너 | KICKR, NEO, Direto… | **FTMS** (+ 경우에 따라 CSCP 병행) | **Cadence**, **Power(옵션)** |

**핵심:** 구현은 **Sensor Input Layer**에서만 갈라지고, 그 아래는 **동일한 effort → 속도 파이프라인**으로 합친다.

### 3.3 Zwift·다른 앱과의 관계

- 동일 스마트폰에서 **같은 트레이너에 Zwift와 동시 BLE 중앙 연결**은 **대부분 불가**에 가깝다.
- **영어**로 명확히 안내: 다른 트레이닝 앱을 끄고 본 앱만 연결할 것.
- 본 앱은 “Zwift 대체”가 아니라 **Street View 실내 라이드** 포지션으로 설명 가능.

## 4. UI/UX 설계 (핵심 화면)

### 4.1 Route Settings 패널

- 패널 안 **“SPEED” 텍스트**를 제거한다.
- 그 자리(또는 동일 행의 라벨 역할)에 **속도계 아이콘 형태의 버튼**을 둔다.
- 버튼에 **연결 상태 배지**(미연결/연결됨)를 작게 표시하면 좋다.
- **툴팁·접근성 라벨은 영어**(예: “Sensors & speed”).

### 4.2 모달(팝업) — 모든 센서 관련 처리의 단일 진입점

**원칙:** 설정 메뉴처럼 보이지 않게 **“연결 → 숫자가 움직임 → (선택) 측정 → 완료”** 순서.

**권장 섹션 순서(실제 문자열은 전부 영어):**

1. **헤더:** 제목 + 닫기
2. **연결 상태:** Disconnected / Scanning / Connected + 디바이스 이름
3. **스캔·목록:** Scan, 디바이스 리스트, Connect / Disconnect
4. **실시간 값:** RPM 큰 표시; FTMS에서 가능하면 **Watt** 표시(옵션)
5. **1분 최대 노력 측정:** 버튼 + 60초 진행 표시 + 안내(최고 저항으로 맞추라는 **짧은 영어** 문구)
6. **결과:** **평균 RPM** 표시, Retake / Use this value
7. **동작 토글:** Sensor-driven speed **On/Off** (기본은 연결 후 On 권장)
8. **부하 힌트(선택, 3단):** Light / Normal / Heavy — 내부는 **capacity 등에 곱하는 단일 계수**만
9. **듀얼 센서:** 두 채널이 살아 있으면 영어 **한 줄 배지**만 (예: *“Dual sensors: speed + cadence”*, 부가 설명은 접기)
10. **고급(접힘, 옵션):** 결합 우선순위 — **Auto(기본) / Speed priority / Cadence priority**
11. **도움말(영어 한 줄):** BLE 거리, 배터리, **다른 앱과 동시 연결 불가** 등

## 5. 속도·노력 모델 (비-AI, 로컬)

### 5.1 사용자에게 보이는 구조

- **슬라이더 `base_speed`:** “전체 난이도·체감 스케일” (기존 UX 유지).
- **센서 쪽:** 실제 페달/휠에서 오는 입력을 **effort(0~상한)** 로 바꾼 뒤,  
  **`display_speed` = `base_speed` × `f(effort)`** 형태의 **고정 수식**(지수·캡 등은 상수로 튜닝, AI 없음).

### 5.2 캘리브레이션

- **1분**, **최고 저항**, **최대 노력** 가정 하에 측정.
- **통계:** 구간 **평균 RPM**을 저장해 개인 상한 앵커로 사용.
- 초보자처럼 후반 RPM이 무너져도 “그날의 1분 전체”를 쓸지, **중간 구간만** 쓸지는 구현 시 결정 가능(계획상 기본은 **전체 1분 평균** 명시 유지).

### 5.3 주행 중 안정화(비-AI)

- **EMA** 등으로 RPM/속도 입력 스무딩.
- **슬라이딩 윈도우**로 최근 분포에서 **capacity** 를 서서히 갱신(장비·컨디션 변화 흡수). 저장은 **요약 스칼라** 위주.
- **가벼운 피로 모델**은 선택(상한 낮게): 과도한 복잡도는 피함.

### 5.4 파워(FTMS, 옵션)

- Watt를 읽을 수 있으면 `effort`에 **고정 비율식**으로 반영 가능(예: `power / threshold`, threshold는 캘리브레이션·로컬 상수에서 유도).
- **AI 없음.** 파워가 없으면 **RPM-only** 경로와 동일 UX.

## 6. 듀얼 센서(케이던스 + 속도) — 결합 규칙

**“기능을 크게 늘리지 않고, 결합 규칙을 명확히 한다.”**

### 6.1 원칙

| 역할 | 내용 |
|------|------|
| **1순위(기준)** | **속도(휠) 센서**가 유효하면 그 신호를 **주 입력**으로 사용 |
| **2순위(폴백)** | 속도가 끊기거나 비정상이면 **케이던스 기반** 추정으로 전환 |
| **보조(둘 다 있을 때)** | 케이던스로 **속도 급변·스파이크** 완화, 짧은 **부스트(상한 캡)** |

### 6.2 유효성(개념)

- `speed_valid`: 최근 N초 내 업데이트, 물리적으로 그럴듯한 변화율
- `cadence_valid`: RPM 하한 이상, 스무딩 후 안정

### 6.3 우선순위(개념 의사코드)

1. `speed_valid` → 속도 센서 기반 입력
2. else `cadence_valid` → 케이던스·캘리브레이션 기반
3. else → **직전 값 감쇠**(끊김 완화)

### 6.4 둘 다 있을 때 보정(비-AI)

- 속도 **급락** + 케이던스 **유지** → 속도 입력을 이전 쪽으로 **완만 보간**(플라이휠 센서 튐 완화).
- 케이던스 **급상승** → **짧은 부스트**(고정 계수·상한).

### 6.5 선택 로컬 캘리브레이션 `k` (듀얼일 때만 의미)

- 동시에 둘 다 유효한 구간에서 **평균 비율** 등으로 `k` 저장: 휠 속도 대표값 ÷ 케이던스.
- 이후 속도 센서가 잠깐 끊기면 `estimated_speed_from_cadence = cadence * k` 로 **연속성** 확보.
- **휠 크기·기어비 수동 마법사는 Free 비권장**(복잡도·실내 의미 약함). `k`는 **측정 기반**이 우선.

### 6.6 UX

- 기본 **자동 결합**. 고급에서만 **Speed priority / Cadence priority**.
- **영어** 배지 한 줄로 충분.

## 7. BLE·아키텍처(요약)

- **Android(Capacitor):** BLE는 WebView 한계를 고려해 **네이티브 브리지 또는 검증된 플러그인**으로 구현 검토.
- **입력 레이어:**
  - CSCP: 케이던스, (있으면) 휠 속도
  - FTMS: 케이던스 + (옵션) 파워, **제어 명령 없음**
- **듀얼 물리 디바이스:** 케이던스 센서 1개 + 속도 센서 1개 **두 연결** 또는 **한 디바이스에 두 특성** — 구현 시 둘 다 가능하게 설계.

## 8. 로컬 저장(예시 키 개념)

- 연결 디바이스 id/이름(복수 가능)
- `sensor_enabled`, `load_hint`
- `calibration_avg_rpm`, 시각
- (듀얼) `speed_cadence_blend_mode`: auto | speed | cadence
- (선택) `wheel_cadence_k`
- `capacity` 요약값 등 — **용량 최소**

## 10. 테스트 시나리오(필수 체크리스트)

- 무센서 / 센서 Off → **기존과 동일** 주행.
- 케이던스만 연결.
- **케이던스 + 속도** 동시 연결: 자동 결합, 속도 끊김 시 폴백.
- FTMS 트레이너: 케이던스·(있으면) 파워.
- BLE 권한 거부, 스캔 0건, 연결 후 끊김.
- **다른 트레이닝 앱 동시 연결 시도** 시 영어 안내.
- 1분 측정 중단·재시도.
