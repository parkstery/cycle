# 메뉴 구조·문서 형식에 대한 의견 및 확정 사항

**코드 작성 없음.** 의견 제시 및 구현 시 참고용 명세만 정리.

---

## 1. 메뉴 전체 펼침 (한 번에 모두 노출)

**요청:** 메뉴가 많지 않으므로 모두 펼친 채로 보여 주고, 사용자가 한 번에 보고 원하는 메뉴를 클릭하게 한다.

**의견:** **동의합니다.**

- 항목 수가 About, Guide(2개 하위), Settings, Legal(4개 하위), Contact 수준이라 한 화면에 모두 넣어도 부담이 적음.
- 접기/펼치기 없이 평면적으로 보여 주면:
  - 탭 수가 줄고,
  - “Legal이 어디 있지?” 같은 탐색이 사라지며,
  - 스마트폰에서도 목록만 스크롤하면 되어 사용성이 좋아짐.
- 다만 **Legal 하위 4개는 “들여쓰기”로 시각적으로 구분**해 두는 것이 좋습니다(아래 3번 참고).

---

## 2. Help → Guide, 하위 제목 변경

**요청:**  
- 상위: **Help** → **Guide**  
- 하위: **Simple Guide**, **User Guide**

**의견:** **동의합니다.**

- “Guide”가 “도움말”보다 기능(안내·가이드)을 더 잘 드러냄.
- “Simple Guide” / “User Guide”는 문서명(SIMPLE_GUIDE_EN.md, USER_GUIDE_EN.md)과도 맞고, 의미도 명확함.

---

## 3. Legal 하위 메뉴 들여쓰기

**요청:** Legal 하위 항목들(Privacy Policy, Terms of Service, Disclaimer, Open Source Licenses)의 들여쓰기가 제대로 되어 있지 않다는 피드백이 여러 번 있었고, 들여쓰기를 해 달라고 하심.

**의견:** **반드시 반영하는 것이 좋습니다.**

- Legal은 “상위 라벨 + 하위 4개” 구조이므로, 하위 4개는 **시각적으로 한 단계 들여쓴 것처럼** 보여야 합니다.
- 구현 시 참고:
  - **패딩/마진:** Legal 하위 `<ul>` 또는 각 `<li>`에 `padding-left`(또는 `margin-left`)를 상위 메뉴(About, Guide, Settings 등)보다 크게 주어, “Legal 소속”이 명확히 보이게 함.
  - **보조선:** 현재처럼 `border-l` 등으로 세로선을 넣었다면, 그 선이 **들여쓴 영역 안**에서만 보이도록 하면 계층이 더 분명해짐.
- “들여쓰기가 안 되어 있다”는 것은 보통 **하위 항목이 상위와 같은 왼쪽 정렬**로 보일 때를 말하는 경우가 많으므로, **하위 항목만 왼쪽에 여백을 두는 것**을 우선 적용하면 됩니다.

(코드는 작성하지 않았으므로, 구현 시 위 방향으로 스타일만 적용하면 됨.)

## 4. Settings 메뉴 추가 위치

**요청:** Guide 아래에 **Settings**를 단일 항목으로 넣고, 클릭 시 설정 화면으로 이동. “미리 삽입해 두어라.”

**의견:** **위치와 역할 모두 적절합니다.**

- Guide(앱 사용 안내) 바로 아래에 Settings(앱 설정)를 두면, “사용법 → 설정” 흐름이 자연스럽습니다.
- Settings는 **하위 없이 단일 항목**으로 두고, 탭 시 기존처럼 별도 설정 화면(패널 또는 전체 화면)으로 이동하면 됩니다.

**구현 시 적용할 메뉴 순서:**

```
Menu
  About
  Guide
    Simple Guide
    User Guide
  Settings          ← 단일 항목, 클릭 시 설정 화면
  Legal
    Privacy Policy
    Terms of Service
    Disclaimer
    Open Source Licenses
  Contact
```

- “미리 삽입”은 **메뉴 목록에 Settings 항목을 추가해 두고**, 클릭 시 이동할 설정 화면은 기존이 있으면 연결하고, 없으면 빈 화면/플레이스홀더라도 두어도 됩니다. (코드는 작성하지 않았으므로, 구현 시 위 순서대로 항목만 넣으면 됨.)

## 5. 문서 형식: 마크다운이 아닌 일반 문서 + 타이틀 스타일

**요청:**  
- 문서 형식은 **마크다운이 아닌 일반 문서**로 한다.  
- **타이틀**은 본문보다 **큰 폰트 + Bold**로 한다.  
- 내용이 복잡하지 않으므로 일반 문서로도 보기에 문제없을 것 같다는 의견.

**의견:** **동의합니다. 일반 문서 + 타이틀만 강조하는 방식으로 가는 것이 좋습니다.**

- **이유 요약:**
  - 앱 내에서 보여줄 텍스트는 법적 문구·안내·연락처 등 **단순한 문단·목록**이 대부분이라, 마크다운 파서 없이 **일반 텍스트 + 제목만 크기/굵기로 구분**해도 가독성이 충분함.
  - 구현이 단순함: 마크다운 렌더러, `dangerouslySetInnerHTML`, 표 처리 등이 필요 없고, **제목용 컴포넌트(큰 폰트 + bold) + 본문용 컴포넌트(일반 폰트)**만 있으면 됨.
  - 표가 있는 문서(Privacy, Contact, Licenses 등)는 “제목 + 본문” 구조로 옮길 때, 표는 **줄 단위로 나열**하거나 **제목: 내용** 형태로 풀어서 써도 이해하는 데 무리가 없음.

- **적용 방식 제안:**
  - **타이틀:** 본문보다 큰 폰트 크기(예: 1.1~1.25em 또는 디자인 시스템의 제목 스타일) + **Bold**.
  - **본문:** 일반 폰트 크기, 일반 굵기. 줄바꿈·단락 구분만 유지.
  - **소제목(절 번호 등):** 필요하면 본문보다 약간 크게 + Bold로 구분해도 됨.
  - **목록:** 마크다운 “-” 대신 일반 텍스트로 줄바꿈으로 나열하거나, 간단한 `<ul>` 스타일만 적용해도 됨.

- **주의할 점:**
  - USER_GUIDE(Detail)처럼 **긴 문서**는 “1. 개요”, “2. 시작하기” 같은 **소제목을 Bold로 두어** 스크롤 시 구간을 찾기 쉽게 하면 좋음.
  - 표는 앱에서는 **표 컴포넌트 없이** “항목: 설명” 또는 “• 항목 – 설명” 형태로 풀어 써도 됨.

**정리:** docs 원본은 마크다운으로 유지하고, **앱에 표시할 때만** “일반 문서 + 큰 폰트·Bold 타이틀” 규칙으로 변환해 넣는 방식으로 결정하시면 됩니다.

## 6. 확정된 메뉴 구조 (구현 시 참고)

| 순서 | 표시 이름 | 비고 |
|------|-----------|------|
| 1 | About | 단일 항목 |
| 2 | Guide | 상위 라벨, 하위 2개 |
| 2-1 | Simple Guide | Guide 하위, **들여쓰기** |
| 2-2 | User Guide | Guide 하위, **들여쓰기** |
| 3 | Settings | 단일 항목, 클릭 시 설정 화면 |
| 4 | Legal | 상위 라벨, 하위 4개, **들여쓰기** |
| 4-1 | Privacy Policy | Legal 하위, **들여쓰기** |
| 4-2 | Terms of Service | Legal 하위, **들여쓰기** |
| 4-3 | Disclaimer | Legal 하위, **들여쓰기** |
| 4-4 | Open Source Licenses | Legal 하위, **들여쓰기** |
| 5 | Contact | 단일 항목 |

- **표시 방식:** 모든 항목 한 번에 펼쳐서 노출(접기 없음).  
- **들여쓰기:** Guide 하위 2개, Legal 하위 4개는 상위보다 왼쪽 여백을 두어 시각적으로 한 단계 안으로 들여쓴 것처럼 표시.

## 7. 문서 형식 확정 (앱 내 표시용)

- **형식:** 마크다운 아님. **일반 문서**(plain text + 간단한 구조).
- **타이틀:** 본문보다 **큰 폰트 + Bold**.
- **본문:** 일반 폰트. 표는 필요 시 문장/목록 형태로 풀어서 표현.

이대로 결정하시면 됩니다.
