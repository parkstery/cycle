# 자전거·도보 경로 탐색 기능 추가 — 해결 방안

## 1. 현재 앱 상태 요약

| 구분 | 현재 구현 | 비고 |
|------|-----------|------|
| **타입** | `types.ts`에 `TravelMode { DRIVING, BICYCLING, WALKING }` 이미 존재 | OSM NAVI의 RouteMode와 역할 동일 |
| **경로 계산** | `App.tsx`의 `calculateRoute(activeMode)`에서 `profile = driving \| cycling \| foot`로 `/api/osrm-route?profile=...` 호출 | **모드별 프로필은 이미 전달 가능** |
| **API** | `api/osrm-route.js` + vite 프록시가 **router.project-osrm.org** 단일 서버에 `car/bike/foot` 프로필로 요청 | 자전거/도보 프로필 지원함 |
| **UI** | car 버튼만 `calculateRoute(mode, false)` 호출, **bike/walk 버튼은 disabled·미연결** | 사용자가 모드를 바꿀 수 없음 → 항상 자동차 경로만 요청됨 |

**결론:** 백엔드와 `calculateRoute`는 이미 모드(자동차/자전거/도보)를 구분할 수 있는 상태이다. “도심 골목길에서 자동차 경로만 나온다”는 현상은 **UI에서 bike/walk를 선택할 수 없고, 따라서 항상 DRIVING(자동차)으로만 요청되기 때문**으로 보는 것이 타당하다.  
추가로, 단일 OSRM 서버의 bike 프로필이 지역에 따라 차량 도로 위주로 나올 수 있으므로, **모드별 전용 서버** 도입은 선택적 개선 사항이다.

---

## 2. OSM NAVI 참고 구현과의 매핑

| OSM NAVI 기능 | 해당 파일/라인 | 우리 앱에서의 대응 |
|---------------|----------------|---------------------|
| 경로 모드 정의 | `/types.ts` RouteMode (car, bike, foot) | **이미 존재**: `types.ts` `TravelMode` (DRIVING, BICYCLING, WALKING) |
| 서버 엔드포인트 분기 | `/services/routingService.ts` — 모드별 **서로 다른 URL** (routed-car / routed-bike / routed-foot) | **현재**: 단일 URL + profile 쿼리 (`api/osrm-route.js`, vite 프록시). **선택 개선**: 모드별 전용 서버 도입 |
| UI 상태 및 API 호출 | `App.tsx` — `routeMode` state, `fetchRoute(routeMode)` | **이미 존재**: `mode` state, `calculateRoute(targetMode)`. **부족**: UI에서 bike/walk 선택 시 `setMode` + 해당 모드로 `calculateRoute` 호출 |
| 모드별 소요시간·표시 | `RouteInfo.tsx` — 자전거/도보 평균 속도로 duration 재계산, 라벨·색상 | **일부 존재**: App.tsx에서 경사 기반 duration(자전거). **추가**: 도보 모드일 때 고정 속도(예: 4.5km/h)로 duration 재계산 및 UI 라벨/색상 |

## 3. 해결 방안 (코드 작성 없이 제안만)

### 3.1 타입 정의 (`types.ts`)

- **유지**: `TravelMode` enum 그대로 사용.
- **(선택)** API/프로필 문자열과 매핑이 여러 곳에 흩어져 있으므로, 한 곳에 모드 → OSRM 프로필 이름 매핑(예: `DRIVING → 'driving'`, `BICYCLING → 'cycling'`, `WALKING → 'foot'`)을 상수/헬퍼로 두면 유지보수에 유리.

---

### 3.2 UI 상태 및 버튼 동작 (App.tsx)

- **선택된 모드 표시**  
  - car / bike / walk 버튼 중 **현재 `mode`**에 해당하는 버튼만 시각적으로 강조(예: 테두리·배경색 차이).
- **car 버튼**  
  - 클릭 시: `setMode(TravelMode.DRIVING)` 후 `calculateRoute(TravelMode.DRIVING, false)` 호출. (이미 `calculateRoute(mode, false)` 형태로 되어 있으면, 모드만 DRIVING으로 맞추면 됨.)
- **bike 버튼**  
  - **disabled 제거**, 클릭 시: `setMode(TravelMode.BICYCLING)` 후 `calculateRoute(TravelMode.BICYCLING, false)` 호출.
- **walk 버튼**  
  - **disabled 제거**, 클릭 시: `setMode(TravelMode.WALKING)` 후 `calculateRoute(TravelMode.WALKING, false)` 호출.
- **Go 버튼**  
  - 현재처럼 “선택된 `mode`”로 경로 탐색 및 시뮬레이션 시작 유지. `inputsMatch` 등에서도 이미 `mode`를 비교하고 있으므로, 모드 변경 시 새로 경로를 요청하도록 그대로 두면 됨.

이렇게 하면 사용자가 car/bike/walk를 선택할 때마다 해당 모드로 OSRM이 요청되고, **자전거/도보 경로 탐색이 동작**한다.

---

### 3.3 라우팅 서버·엔드포인트 (api/osrm-route.js 또는 별도 routingService)

**옵션 A — 최소 변경 (현재 구조 유지)**  
- `router.project-osrm.org` 단일 서버 + 쿼리 파라미터 `profile=driving|cycling|foot` 유지.  
- 클라이언트에서 이미 `profile`을 보내고 있으므로, **UI만 3.2처럼 연결하면** 자전거/도보 경로가 바로 요청됨.  
- 일부 지역에서는 자전거 전용 도로·골목길 반영이 약할 수 있음.

**옵션 B — OSM NAVI 방식: 모드별 전용 서버**  
- OSM NAVI처럼 **모드별로 서로 다른 base URL** 사용:
  - 자동차: `https://routing.openstreetmap.de/routed-car/route/v1/driving`
  - 자전거: `https://routing.openstreetmap.de/routed-bike/route/v1/driving`
  - 도보: `https://routing.openstreetmap.de/routed-foot/route/v1/driving`
- **구현 위치**: `api/osrm-route.js`(또는 Vercel 배포 시 동일 로직)에서 `profile`(또는 mode)에 따라 `getEndpoint(profile)`로 base URL을 선택한 뒤, 기존과 동일한 쿼리(coords, overview, geometries 등)로 요청.
- **주의**:  
  - `routing.openstreetmap.de` 사용 정책·가용성 확인.  
  - 응답 형식(geometry 인코딩, 필드명 등)이 `router.project-osrm.org`와 동일한지 확인. 다르면 응답을 현재 형식으로 맞추는 변환만 추가하면 됨.

**권장**: 먼저 **옵션 A**로 UI만 연결해 자전거/도보가 동작하는지 확인한 뒤, 도심 골목길 등에서 경로 품질이 만족스럽지 않으면 **옵션 B**로 전환 검토.

---

### 3.4 모드별 소요 시간·정보 표시 (App.tsx 또는 RouteInfo 성격의 컴포넌트)

- **자동차**  
  - OSRM이 반환한 `duration` 그대로 사용하거나, 현재 로직 유지.
- **자전거**  
  - 현재처럼 **경사 기반 보정** 유지: 사용자 `speedKmH`, 경사 구간별 factor 적용해 `calculatedSeconds` 계산 후 `durText` 설정. (이미 구현된 부분 유지.)
- **도보**  
  - OSM NAVI 참고: **고정 평균 속도**(예: 4.5km/h)로 거리 기반 duration 재계산.  
  - `TravelMode.WALKING`일 때만 이 로직을 타도록 분기 추가.  
  - 수식 예: `duration_seconds = totalDistanceMeters / (4.5 * 1000 / 3600)`.
- **라벨·색상**  
  - 경로 정보 영역에 현재 모드 표시(예: "자동차 경로", "자전거 경로", "도보 경로").  
  - 필요 시 모드별 색상/아이콘 적용(예: 자전거 녹색, 도보 파란색).

---

### 3.5 저장/즐겨찾기 연동

- **SavedRoute**에 **mode**(또는 `TravelMode`) 필드 추가.
- 저장 시: 현재 `mode`를 함께 저장.
- 불러올 때: `setMode(loaded.mode)` 후, 필요 시 `calculateRoute(loaded.mode, false)`로 해당 모드 경로 재탐색.  
  → 사용자가 저장한 “자전거 경로”를 불러왔을 때 자전거 모드로 다시 탐색되도록 일치시킴.

---

### 3.6 (선택) 시뮬레이션·코칭

- 주행 시뮬레이션은 현재도 “경로 좌표 + 고도” 기준이므로, **모드와 무관하게 동일한 경로 재생**이 가능.
- 코칭 멘트는 자전거 중심으로 되어 있다면, **도보 모드**일 때는 다른 문구로 전환하거나 비활성화하는 분기를 두는 것을 고려할 수 있음.

---

## 4. 작업 순서 제안

1. **UI 연결 (3.2)**  
   - bike/walk 버튼 활성화, 클릭 시 `setMode` + `calculateRoute(해당 모드, false)`, 선택 모드 시각 강조.
2. **동작 확인**  
   - 자전거/도보 선택 시 `profile=cycling`, `profile=foot`로 요청되는지, 경로가 맵에 표시되는지 확인.
3. **도보 소요 시간 (3.4)**  
   - WALKING일 때 고정 속도로 duration 재계산 및 표시.
4. **라벨/색상 (3.4)**  
   - 현재 모드 문구 및 테마 적용.
5. **(선택) 모드별 전용 서버 (3.3 옵션 B)**  
   - 품질 개선이 필요할 때만 `routing.openstreetmap.de` 분기 도입.
6. **(선택) 저장/불러오기 (3.5)**  
   - SavedRoute에 mode 포함, 로드 시 모드 복원.

## 5. 요약 표

| 기능 구분 | 파일 경로 | 핵심 조치 |
|-----------|-----------|-----------|
| 타입 정의 | `types.ts` | TravelMode 유지; (선택) 모드↔프로필 문자열 매핑 한 곳에 정리 |
| 서버 분기 | `api/osrm-route.js`, vite `vite.config.ts` | 현재: profile만 전달. 개선 시: 모드별 base URL 분기 (routing.openstreetmap.de) |
| UI·상태 | `App.tsx` (경로 탐색 컨테이너) | car/bike/walk 클릭 시 setMode + calculateRoute(해당 모드); 선택 모드 강조; Go는 현재 mode 유지 |
| 소요 시간·표시 | `App.tsx` (duration 계산·표시) | 자전거: 기존 경사 보정 유지; 도보: 고정 속도(예: 4.5km/h)로 재계산; 모드 라벨·색상 |
| 저장/불러오기 | `App.tsx`, `types.ts` (SavedRoute) | SavedRoute에 mode 추가; 로드 시 setMode(loaded.mode) 및 필요 시 재탐색 |

이 순서대로 적용하면, **car / bike / walk 세 종류 경로 탐색을 모두 지원**하고, 자전거 경로의 목표(도심·골목길 포함)에 맞춰 필요 시 서버만 전용 엔드포인트로 바꾸면 된다.
