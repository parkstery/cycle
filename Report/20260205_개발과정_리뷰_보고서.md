## 2. 초기 계획 대비 개발 과정

### 2.1 출발점 (Analysis.md)

- **레거시:** 단일 파일 Vanilla JS, 데스크톱 중심 레이아웃, 마우스 기반 인터랙션.
- **목표:** 스마트폰 전환을 위한 모바일 퍼스트 설계, Bottom Sheet·FAB, 터치 최적화.
- **기술 스택:** React(함수형), Tailwind CSS, Recharts(고도 차트).
- **기능:** AI 사이클 코칭(Gemini), 실시간 위치 추적(Geolocation), Street View·2D 지도 동기화.

### 2.2 계획 대비 달성 현황

| 계획 항목 | 상태 | 비고 |
|-----------|------|------|
| React + Tailwind | ✅ 완료 | 함수형 컴포넌트, Hooks, Vite 빌드 |
| Recharts 고도 차트 | ✅ 완료 | ElevationChartView.tsx, ReferenceLine 동기화 |
| AI 코칭 | ✅ 완료 | 경사→저항 규칙 + phraseManifest + TTS (Gemini → 로컬 전환) |
| Street View·지도 동기화 | ✅ 완료 | 더블 버퍼, 점진적 로딩, GOOGLE→DEFAULT 폴백 |
| Bottom Sheet / FAB | ⚠️ 부분 | 접이식 패널·플로팅 버튼으로 유사 구현 |
| 실시간 Geolocation | ❌ 미구현 | 시뮬레이션 모드만 지원 |
| 컴포넌트/훅 분리 | ⚠️ 부분 | Map/Directions/Simulation이 App.tsx 내부에 집중 |

핵심 시나리오(경로 설정 → 고도 확인 → Street View 시뮬레이션 → AI 코칭)는 **전반적으로 구현 완료**된 상태이다.

## 3. 아키텍처·기술 선택 리뷰

### 3.1 비용·의존성 관리

- **경로 탐색:** Google Directions 대신 **OSRM** (Vercel API 프록시) 사용 → Google API 비용 절감.
- **지오코딩:** Google Geocoder 대신 **Nominatim** (역지오코딩·검색·주소→좌표) → 오픈소스 전환.
- **고도:** Google Elevation 대신 **Open-Elevation API** → 경로당 1회 POST, 캐시 적용.
- **AI 코칭:** Gemini API 의존 제거 → **로컬 규칙(경사→저항) + phraseManifest + 브라우저 TTS**로 무료·오프라인 대응.
- **지도:** 일부 문서에서 Leaflet+OSM 전환 논의가 있으나, 현재 코드는 **Google Maps JS**(지도·Street View) 사용. Street View는 Google 전용 리소스로 유지.

이를 통해 **Google 의존도는 지도·Street View에 한정**되고, 나머지 GIS·코칭 파이프라인은 오픈소스·로컬 처리로 정리되었다.

### 3.2 배포·인프라

- **Vercel:** SPA 정적 배포 + Serverless API (`/api/nominatim-search`, `/api/nominatim-reverse`, `/api/osrm-route`).
- **PWA:** manifest.json, Service Worker(sw.js) 등록. (일부 환경에서 SW 해제·캐시 삭제 로직 존재.)
- **트래픽:** 세션당 Vercel 요청은 정적 4~8건 + 검색·클릭·경로 계산에 따른 API 건수; Nominatim 1 req/s 제한 대비 클라이언트 스로틀·캐시 적용.

## 4. 코드 품질·유지보수성 리뷰

### 4.1 강점

- **타입 정의:** `types.ts`에 RouteInfo, ElevationPoint, SimulationState, CoachingData, SavedRoute, PanoDataItem 등이 명확히 정의되어 있어 도메인 이해와 리팩터링에 유리함.
- **서비스 분리:** `services/` 하위에 aiCoach, nominatim, openElevation, geoUtils, phraseManifest, plusCode 등이 분리되어 테스트·교체가 용이함.
- **Ref 활용:** 지도·파노라마·마커 등 인스턴스를 ref로 보관해 불필요한 리렌더를 줄이는 구조.

### 4.2 개선 필요 사항

| 항목 | 내용 |
|------|------|
| **단일 파일 비대화** | App.tsx가 1,800줄 이상. 지도/경로/시뮬레이션/Street View/패널 등을 컴포넌트·훅(Map, useSimulation, useStreetView 등)으로 분리하면 가독성·테스트·협업이 개선됨. |
| **전역 타입** | `declare var google: any` 사용. `@types/google.maps` 도입 시 타입 안정성·자동완성 향상. |
| **환경 변수** | API 키 등 필수 항목에 대한 `.env.example` 및 README 명시가 있으면 온보딩·배포 실수가 줄어듦. |
| **CSS 진입점** | Tailwind 진입점(main.css)과 index.html 참조 관계를 한 곳에 정리해 두면 빌드·스타일 이슈 추적이 쉬움. |

## 5. 기능별 개발 과정 요약

- **지도·경로:** 출발/도착/경유 설정, OSRM 경로, 2m 밀도 보간, Open-Elevation 고도, 경사 반영 주행 시간 → WEB GIS 핵심 플로우 완성.
- **Street View:** 더블 버퍼·전환 전략·점진적 로딩(초기 200m + 온디맨드)·전방 위주 탐색으로 끊김·검은 화면 완화.
- **시뮬레이션:** 속도(10~100 km/h) 기반 인덱스 진행, 고도 차트 동기화, 완주 시 TTS.
- **AI 코칭:** 예측 코칭(cachedCoaching)·21스텝 주기·시작/종료 멘트(getCourseBriefing, getRideEncouragement)까지 일관된 UX.
- **UX:** 장소 검색(Nominatim), 즐겨찾기(My Routes), 배경 음악, Go 버튼·카운트다운, 교통 레이어 등으로 사용 시나리오를 보완.
