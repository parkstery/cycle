# 거리뷰 연속성 문제 분석 및 해결방안

## 1. 현상

- **증상**: 주행 노선의 거리뷰 이미지가 많이 생략된 채 표시됨 (예: 200m 주행 시 2~3장만 전환).
- **원칙**: 트래픽 저감은 **주행 중 경로상의 연속적인 거리뷰 기능 유지**를 전제로 해야 하며, 기능 저하가 있어서는 안 됨.

---

## 2. 원인 분석

### 2.1 현재 구조

- **PREPARING 단계**: 경로 확정 후 `preFetchStreetViewData()`가 경로를 **거리 기준 100m 간격**으로 샘플링하여 각 위치에서 `getPanorama` 1회씩 호출. 획득한 `panoId`·`heading`을 `panoData[]`에 저장.
- **RUNNING 단계**: 시뮬레이션의 `currentIndex`(경로 상 인덱스)에 대해 `getPanoDataForIndex(panoData, currentIdx)`로 **현재 위치 이하에서 가장 큰 pathIndex를 가진 pano**를 선택해 `setPanoramaViewByPanoId(panoId, heading)` 호출. **주행 중에는 getPanorama API를 호출하지 않음**(트래픽 제로 유지).

### 2.2 생략이 발생하는 직접 원인

- **샘플 간격이 100m로 과도하게 큼**  
  - 200m 구간이면 샘플은 **0m, 100m, 200m** 세 지점뿐 → `panoData` 항목도 최대 3개.  
  - `getPanoDataForIndex`는 “현재까지 지나온 샘플 중 마지막”만 사용하므로, **실제로 전환되는 화면도 2~3장**이 됨.
- 즉, **거리뷰 전환 빈도 = 샘플 개수 = (총 거리 / 100m) + 1** 이 되어, 100m마다 한 번씩만 화면이 바뀌므로 연속성이 크게 떨어짐.

### 2.3 트래픽 최적화와의 관계

- 트래픽 저감을 위해 **PREPARING 시 샘플 수를 줄이기 위해 100m 간격**을 쓴 것으로 보임.
- 그 결과 **주행 중 API 호출은 0으로 유지**되었지만, **사전에 쌓아 둔 pano 개수가 너무 적어** “연속적인 거리뷰”라는 핵심 기능이 약화됨.
- **원칙 위반**: “기능 유지 범위 내에서의 트래픽 감소”가 아니라 “트래픽 감소 우선”으로 간격을 크게 잡아 기능이 저하된 상태.

---

## 3. 해결 방향 (원칙 준수)

- **주행 중(RUNNING) getPanorama 호출은 계속 0회 유지** → 트래픽 저감 목표 유지.
- **연속적인 거리뷰**를 복구하려면 **PREPARING 단계에서 경로를 더 촘촘히 샘플링**해, 같은 원리(거리 기준 샘플 → pathIndex → 주행 시 선택)를 유지하되 **전환 빈도를 높이는 것**이 유일한 방법.

---

## 4. 구체적 해결방안

### 4.1 권장: 샘플 간격을 100m → 30m로 축소

- **변경 내용**: `preFetchStreetViewData` 내 **거리 샘플 간격을 100m에서 30m로 변경**.
- **효과**:
  - 200m 구간: 기존 2~3장 → **약 7장** 수준으로 전환 빈도 증가 → 연속 체감 크게 개선.
  - 주행 중 API 호출: **그대로 0회** (PREPARING에서만 호출 수 증가).
- **트래픽 영향**:
  - PREPARING 시 `getPanorama` 호출 수 = `ceil(총거리(m) / 30)` (기존은 `/100`).
  - 예: 2km 경로 → 기존 약 21회 → 변경 후 약 67회. **경로당 1회만 발생**하므로, “주행 중 트래픽 0”이라는 목표는 유지하면서 연속성만 복구.

### 4.2 장거리 경로 시 트래픽 제어 (선택)

- 매우 긴 경로(예: 10km 이상)에서 PREPARING 호출 수가 과도해지면, **구간별로 간격을 완만히 조정**하는 방식 적용 가능.
  - 예: 처음 2km는 30m, 이후는 50m 등으로 **구간별 가변 간격**.
- 적용 시에도 “주행 중 API 0회”와 “연속 거리뷰 체감”을 만족하는 범위에서만 완화하는 것이 원칙.

### 4.3 구현 시 유의사항

- **lookup 로직 유지**: `getPanoDataForIndex`(현재 위치 이하 최대 pathIndex)와 `setPanoramaViewByPanoId`만 사용하는 구조는 그대로 두고, **샘플 생성 간격(intervalM)만 30m로 변경**하면 됨.
- **실패 구간**: 특정 위치에서 `getPanorama`가 실패하면 해당 샘플만 누락되고, 인접 샘플까지의 구간이 길어질 수 있음. 이는 기존과 동일한 이슈이며, 30m로 촘촘히 채우면 실패 시에도 다음 유효 pano까지의 공백이 짧아져 체감 품질이 좋아짐.

---

## 5. 결론

| 항목 | 내용 |
|------|------|
| **원인** | PREPARING 단계의 거리뷰 샘플 간격 100m가 과대하여, 동일 구간에서 전환되는 pano 수가 2~3장 수준으로 적음. |
| **해결** | 샘플 간격을 **30m**로 축소. 주행 중 API 호출은 그대로 0회로 두고, PREPARING 시 샘플 수만 증가시켜 연속 거리뷰를 복구. |
| **원칙 준수** | “연속적인 거리뷰 유지”를 전제로, 트래픽 저감(주행 중 제로 트래픽)은 유지한 채 기능만 복구. |

이에 따라 **코드 변경**: `App.tsx`의 `preFetchStreetViewData` 내 `intervalM = 100` → `intervalM = 30`으로 수정함.
