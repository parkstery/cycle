# 거리뷰 생략 없음·초기 로딩 개선 및 트래픽 저감 방안 검토 보고

## 1. 현재 방식의 문제 (요약)

| 문제 | 내용 |
|------|------|
| **첫째** | 초기 거리뷰 로딩 시간이 길다. 사용자가 기다리지 않는다. |
| **둘째** | 거리뷰 이미지 생략이 많다. (생략 없이 모두 디스플레이하기를 원함.) |

## 2. 요구하신 개선 방향

1. **주행 방향의 거리뷰를 생략 없이 모두 디스플레이**  
   - 건물 내부 등 비일관 화면이 갑자기 나오면 안 되고, **주행 방향·일관성 유지**.
2. **기능 저하 없이, 특히 “경로 상 거리뷰 생략 없음”을 전제로 트래픽 저감**이 도입되어야 함.

---

## 3. 기술적 제약 정리

### 3.1 “생략 없음”이 의미하는 것

- 경로를 따라 **필요한 모든 구간**에서 적절한 거리뷰가 나와야 함.
- Google Street View는 도로를 따라 보통 **약 10~20m 간격**으로 파노라마가 있음.
- 따라서 “생략 없음”에 가깝게 하려면, **최소 10~15m 단위**로 경로 상 위치를 커버해야 함. (현재 30m 간격은 여전히 구간마다 “한 장”만 쓰는 식이라, 체감상 생략이 있음.)

### 3.2 트래픽이 발생하는 지점

- **getPanorama(location)** 호출 1회 = 해당 위치에서 사용할 **panoId**를 알아내는 비용.
- panoId를 알면 **setPano(panoId)** 만으로 화면 전환 가능(추가 API 없음).
- 즉, “몇 개의 위치에서 panoId를 알아내느냐”가 호출 횟수 = 트래픽.

### 3.3 세 가지 목표의 관계

| 목표 | 의미 |
|------|------|
| **A. 생략 없음** | 경로 전체를 10~15m 단위로 커버 → 필요한 pano 개수 많음 (예: 2km → 130~200개 수준). |
| **B. 초기 로딩 짧음** | 주행 시작 전에 “많은” 것을 기다리지 않음. |
| **C. 트래픽 저감** | getPanorama 호출 수를 줄이거나, 최소한 “주행 중 호출 0”을 유지하고 싶음. |

- **현재 방식**: C를 위해 “주행 중 0회”로 두고, 전부 PREPARING에서 미리 호출 → A를 만족하려면 샘플 수가 많아지고, 그만큼 **초기 로딩(B)이 길어짐**.
- **반대로** B를 만족하려면 “시작 전에 적게만 받고, 나머지는 주행 중 채우는” 구조가 필요 → 주행 중에도 getPanorama 호출 발생 → C 중 “주행 중 0회”는 포기해야 함.

정리하면:

- **“생략 없음(A)” + “초기 로딩 짧음(B)”** 을 동시에 만족하려면,  
  **일부는 주행 시작 후에** pano를 가져와야 함 → **주행 중에도 API 호출이 발생**합니다.
- **“생략 없음(A)” + “주행 중 API 0회(C)”** 를 고수하면,  
  **전부 시동 전에** 가져와야 함 → **초기 로딩(B)이 길어질 수밖에 없습니다.**

즉, **A·B·C를 동시에 만족하는 것은 구조적으로 불가능**합니다.  
그래서 “생략 없음 + 기능 저하 없음”을 전제로 트래픽을 **최대한** 줄이는 방안만 제안할 수 있습니다.

---

## 4. 방안 검토

### 4.1 방안 1: 전부 PREPARING에서 조밀하게 미리 받기 (현재 방식 강화)

- **내용**: 간격을 10~15m로 줄여, 경로 전체를 미리 조밀하게 pre-fetch. 주행 중에는 캐시만 사용(호출 0).
- **장점**: 주행 중 API 0회 유지. 생략을 거의 없앨 수 있음.
- **단점**:  
  - 2km 기준으로도 130~200회 호출 + 호출 간 80ms 지연 → **초기 로딩 10~20초 이상** 가능.  
  - 사용자가 “초기 로딩을 기다리지 않는다”는 요구와 **직접 충돌**.
- **결론**: “초기 로딩 짧음” 조건을 포기할 때만 선택 가능. 요구사항과 맞지 않음.

### 4.2 방안 2: 빠른 시작 + 주행 중 점진적 로딩 (권장)

- **내용**  
  - **시작**: 처음 100~200m만 빠르게 pre-fetch(몇 개~十여 개 pano)하고, 곧바로 주행 시작.  
  - **주행 중**:  
    - 현재 위치·주행 방향 기준으로 “앞쪽” 구간이 캐시에 없으면, 그 구간에 대해 **getPanorama** 호출 후 캐시에 저장.  
    - 이미 캐시된 pano는 **setPanoramaByPanoId** 만 사용(추가 API 없음).  
  - **일관성**:  
    - 요청 위치를 **경로 상 좌표**로만 두고, 도로 밖/건물 내부로 치우치지 않도록 radius·경로 스냅 유지.  
    - 한 번 얻은 panoId의 **links(인접 파노라마)** 를 활용하면, 같은 도로 위 인접 pano는 추가 getPanorama 없이 전환 가능(선택 사항).
- **장점**:  
  - **초기 로딩 짧음**: 소량만 받고 바로 시작.  
  - **생략 최소화**: 주행하면서 필요한 구간을 채우므로, 설계만 잘 하면 경로 상 거리뷰를 빠짐없이 보여줄 수 있음.  
  - **주행 방향·일관성**: 경로 상 위치만 사용하고, 건물 내부 등은 사용하지 않도록 로직으로 제어 가능.
- **단점**:  
  - **주행 중 getPanorama 호출 발생** → “주행 중 0회”는 포기.  
  - 대신 **캐시**를 쓰므로 같은 구간 재방문 시 재호출 없음. **총 호출 수**는 “경로 상 필요한 pano 개수” 수준으로 유지 가능.
- **트래픽 저감**:  
  - 동일 구간에 대해 **한 번만** 호출하고 캐시.  
  - “앞쪽 N m만 미리 요청” 등으로 동시/연속 요청 수를 제한해 부하·피크 완화.  
  - 장기적으로는 **세션/로컬 캐시**까지 두면 동일 경로 재주행 시 트래픽 추가 감소 가능.

이 방안이 **“생략 없음 + 초기 로딩 짧음”** 을 동시에 만족시키는 유일한 구조**에 가깝고, 그 전제 하에서 트래픽을 “기능을 깎지 않고” 줄이는 현실적 방법입니다.

### 4.3 방안 3: 하이브리드 (최소 pre-fetch + 백그라운드 연속 수집)

- **내용**:  
  - 주행 시작은 방안 2와 동일하게 **짧은 구간만** pre-fetch 후 바로 시작.  
  - 주행이 진행되는 동안 **백그라운드**에서 “아직 안 간 구간”을 미리 순차적으로 getPanorama로 채움.  
  - 화면 표시는 “캐시에 있으면 캐시, 없으면 당장 필요한 만큼만 on-demand”로 하면, 백그라운드가 따라오지 못한 구간도 생략 없이 채울 수 있음.
- **특징**:  
  - 방안 2와 동일한 트레이드오프(주행 중 호출 있음).  
  - 구현이 더 복잡하지만, “앞으로 갈 구간”을 미리 채워서 끊김을 줄일 수 있음.

---

## 5. 주행 방향·일관성 유지 (건물 내부 등 방지)

- **위치 선택**: getPanorama를 호출할 때 **항상 경로(path) 상의 점**만 사용.  
  경로에서 현재/앞쪽 위치를 거리로 샘플링(예: 10~15m 간격)하면, 도로 중앙/차선 근처가 선택됨.
- **radius**: getPanorama의 검색 반경을 **작게**(예: 20~50m) 유지해, 도로가 아닌 건물 내부 등이 잘못 선택될 확률을 줄임.
- **실패 시**: 특정 위치에서 Street View가 없으면, **경로 상 다음/이전 샘플**로 대체 후, 가능한 한 도로 위 pano만 사용하도록 로직 설계.

이렇게 하면 “주행 방향의 거리뷰만, 생략 없이, 일관되게” 보여주는 쪽에 가깝게 맞출 수 있습니다.

---

## 6. 솔직한 결론 및 권장

- **“경로 상 거리뷰 생략 없이 디스플레이”** 와 **“초기 로딩 짧음”** 을 **동시에** 만족시키려면,  
  **주행 중에 필요한 구간을 채우는(점진적/온디맨드 로딩)** 방식이 **필수**입니다.  
  그 경우 **“주행 중 getPanorama 0회”** 는 유지할 수 없습니다.
- **“생략 없음 + 기능 저하 없음” 전제 하에서** 트래픽을 줄이는 것은 다음처럼만 가능합니다.  
  - 주행 중 호출은 **필요한 구간만**, **한 번씩만** 하도록 하고,  
  - **캐시**로 재호출을 막고,  
  - 요청 간격/동시 요청 수를 제한해 **피크 트래픽**을 완화하는 것.  
  “주행 중 0회”라는 목표는 이 전제와 양립하지 않습니다.

**권장**:  
**방안 2(빠른 시작 + 주행 중 점진적 로딩)** 를 기본으로 하고,  
- 경로 상 **10~15m 단위**로 “필요한 pano”를 정의하고,  
- 시작 시 **앞쪽 100~200m만** 빠르게 받은 뒤 곧바로 주행 시작,  
- 주행 중에는 “캐시에 없을 때만” 해당 구간에 대해 getPanorama 호출 후 캐시·표시,  
- 호출은 **캐시 미스 시에만**, **경로 상 위치만** 사용해 **주행 방향·일관성** 유지  

하는 식으로 설계·구현하는 것이,  
“생략 없음 + 초기 로딩 짧음 + 기능 저하 없이 트래픽 최소화”를 모두 만족시키는 한, **현실적으로 도달 가능한 선**입니다.

이 전제 하에 트래픽 저감 방안 도출은 위와 같이 가능하며,  
“주행 중 0회”를 포기하지 않고는 **생략 없음 + 빠른 시작**을 동시에 만족시키는 것은 **기술적으로 불가능**하다는 점을 사실대로 보고합니다.
