# 1km 구간: 현재 방식 vs 성능 최우선 방식 — API 호출 횟수 비교

## 비교 대상 정리

| 구분 | 현재 방식 | 성능 최우선 방식 |
|------|-----------|------------------|
| **구간 로드** | 처음 200m만 프리페치 → 주행 중 200m 끝 근처에서 다음 200m 온디맨드 (총 5회 세그먼트) | 1km **전 구간** 한 번에 프리페치 |
| **샘플 간격** | 7m | 7m (동일) |
| **샘플당 호출** | 반경 30m → 20m → 15m 순차 시도, 실패 시 findStreetView(50). 각 단계마다 getPanorama 1~2회(GOOGLE→DEFAULT) | **반경 50m 1회만** (getPanorama 1~2회) |
| **샘플 간 지연** | 80ms | 없음 (또는 병렬화로 무의미) |
| **요청 방식** | 순차 (샘플 하나씩) | 병렬 가능 (동시 N개) |

---

## 1. 현재 방식 — 1km 구간 총 API 호출 횟수

### 세그먼트 구성

- 초기: **0 ~ 200m** 프리페치
- 주행 중: 캐시 끝(pathIndex - 150) 근처에서 **다음 200m**씩 추가 요청  
  → 1km이면 약 **5개 세그먼트** (0–200, 210–410, 410–610, 610–810, 810–1000 등)

### 세그먼트당 샘플 수

- 200m, interval 7m → `floor(200/7) + 1 = 29`개 샘플

### 샘플 1개당 호출 횟수 (현재 로직)

- **findStreetViewInDirection** 반경 30m → 20m → 15m (각각 getPanoramaWithFallback 1회 = 1~2회)
- 실패 시 **findStreetView(50)** 1회 (1~2회)
- 따라서 **샘플당 1~8회** (최선 1회, 최악 8회)

### 1km 총합 (현재)

| 항목 | 계산 | 결과 |
|------|------|------|
| 총 샘플 수 | 5 세그먼트 × 29 샘플 | **145개** |
| 최소 호출 | 145 × 1 | **145회** |
| 최대 호출 | 145 × 8 | **1,160회** |
| 일반적 범위 | 대부분 1~2회/샘플 | **약 145~290회** |

---

## 2. 성능 최우선 방식 — 1km 구간 총 API 호출 횟수

### 구성

- 1km **전 구간**을 한 번에 프리페치
- 샘플당 **반경 50m로 1번만** getPanoramaWithFallback 호출 (GOOGLE → 실패 시 DEFAULT 1회)
- 샘플당 **1~2회**로 고정

### 샘플 수

- 1km, interval 7m → `floor(1000/7) + 1 = 143`개 샘플

### 1km 총합 (성능 최우선)

| 항목 | 계산 | 결과 |
|------|------|------|
| 총 샘플 수 | 1회 배치 | **143개** |
| 최소 호출 | 143 × 1 | **143회** |
| 최대 호출 | 143 × 2 | **286회** |
| 일반적 범위 | 1~2회/샘플 | **약 143~286회** |

---

## 3. 1km 기준 API 호출 횟수 비교표

| 구분 | 현재 방식 | 성능 최우선 방식 |
|------|-----------|-------------------|
| **총 샘플 수** | 145 (5×29) | 143 |
| **최소 호출** | **145회** | **143회** |
| **일반적** | **약 145~290회** | **약 143~286회** |
| **최대 호출** | **1,160회** | **286회** |

---

## 4. 왜 이렇게 차이가 나는가

### 현재 방식이 최대치에서 훨씬 많은 이유

1. **샘플당 체인**  
   반경 30m → 20m → 15m → findStreetView(50)까지 **최대 4단계**이고, 각 단계마다 getPanorama를 1~2회(GOOGLE 후 DEFAULT) 호출할 수 있어 **샘플당 최대 8회**까지 갑니다.

2. **세그먼트 수**  
   200m 단위로 나누어도 1km이면 샘플 수는 29×5 ≈ 145로, 전 구간 한 번(143)과 비슷합니다. 차이는 **샘플당 호출 수**에서 납니다.

3. **결과**  
   최악의 경우(파노라마가 잘 안 나오는 구간이 많을 때) 현재 방식은 **1,160회**, 성능 최우선은 **286회**로, **약 4배** 차이가 납니다.

### 성능 최우선이 호출이 적은 이유

- 샘플당 **한 번만** 넉넉한 반경(50m)으로 조회하므로, **1~2회**로 고정.
- 반경·폴백 체인을 없애서 “실패 시 재시도”로 인한 추가 호출이 없음.

---

## 5. 정리

- **최소/일반 구간**: 두 방식 모두 **약 143~290회** 수준으로 비슷함.
- **최대(최악 시나리오)**:  
  - **현재**: **1,160회** (샘플당 최대 8회 × 145 샘플)  
  - **성능 최우선**: **286회** (샘플당 최대 2회 × 143 샘플)  
  → **현재 방식이 최대 시 약 4배 더 많이** 호출할 수 있음.

즉, **1km 기준으로는 성능만 고려한 “전 구간 한 번 + 샘플당 1회 조회” 방식이 API 호출 횟수도 더 적고**, 주행 중 추가 요청이 없어 체감 성능도 더 좋습니다.
