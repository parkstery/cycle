# 거리뷰 “뒤로 지나가는” 현상 및 검은 화면 원인·개선 방안

**작성일:** 2025-01-31  
**목적:** (1) 거리뷰가 뒤로 지나가는 듯 보이는 현상과 검은 화면이 잠깐 나오는 현상의 원인 정리, (2) 검은 화면(스틸사진 느낌)이 나오지 않게 할 수 있는 구체적 방안 제시.

---

## 1. 현상 정리

| 현상 | 설명 |
|------|------|
| **뒤로 지나가는 듯 보임** | 거리뷰 화면이 전방이 아니라 후방(또는 반대 방향)으로 진행하는 것처럼 보이는 경우. |
| **검은 화면이 잠깐 보였다가 다음 장면** | 파노라마 전환 시 짧은 순간 검은색(또는 빈) 화면이 보였다가 새 파노라마가 나타나는 경우. |

---

## 2. 원인 분석

### 2.1 “뒤로 지나가는 듯 보이는” 경우의 원인

- **시선 방향(heading)과 실제 파노라마 위치가 어긋나는 경우**
  - **방향 필터 실패 후 비방향 폴백:** `findStreetViewInDirection`으로 전방(±90°) 파노라마를 찾지 못하면, `findStreetView`(방향 무관)로 “가장 가까운” 파노라마를 쓸 수 있음. 이때 **경로 뒤쪽·반대편**에 있는 파노라마가 선택되면, 같은 heading을 넣어도 “전방”이 아니라 뒤쪽 풍경이 보여 **뒤로 가는 느낌**이 남.
  - **panoData의 heading 오류:** pre-fetch 시 `heading = computeHeading(pathPoint, path[nextIdx])`로 계산하지만, 샘플 위치(pathIndex)와 실제 사용 시점의 currentIdx가 많이 차 나면 “앞을 보는” 각도가 경로 진행과 맞지 않아, 일시적으로 반대 방향처럼 보일 수 있음.
  - **같은 파노라마·다른 위치:** 한 파노라마가 경로의 여러 지점에서 재사용될 때, 경로 상 “앞”이 파노라마 좌표계에서는 “뒤”에 해당하는 경우(예: 도로 반대편 캡처), 동일 heading이라도 진행 방향과 반대로 보일 수 있음.

- **현재 구현의 선택 로직**
  - `getPanoDataForIndex`: **pathIndex ≤ currentIdx** 인 것 중 **pathIndex가 가장 큰** 파노라마를 선택. 즉 “현재 위치보다 앞선” 파노라마는 쓰지 않음. 따라서 “앞쪽 파노라마를 잘못 골라서 뒤로 가는 느낌”보다는, **선택된 파노라마의 heading이 경로 진행과 반대**이거나, **폴백으로 선택된 파노라마 위치가 경로 뒤쪽**인 경우가 원인일 가능성이 큼.

**요약:**  
“뒤로 지나가는” 느낌은 주로 **(1) 방향 필터 실패로 후방/측방 파노라마가 선택되거나, (2) 해당 파노라마에 적용한 heading이 경로 진행 방향과 반대로 해석되는 경우**에 발생한다고 보는 것이 타당함.

---

### 2.2 “검은 화면이 잠깐 보였다가 다음 장면”의 원인

- **이중 버퍼 전환 시점**
  - 백그라운드 버퍼(nextPano)에 `setOptions({ pano: panoId, pov: { heading, pitch: 0 }, visible: true })`를 넣은 뒤, **일정 시간(50ms / 80ms) 또는 `links_changed` / 500ms 타임아웃** 후에만 스왑(doSwap)하고 있음.
  - Google Street View API에는 **“타일이 모두 로드되어 화면에 그려졌다”**를 알리는 이벤트가 **없음**. `status_changed`와 `getStatus() === 'OK'`는 **메타데이터(파노라마 ID·링크 등)가 준비된 시점**을 의미할 뿐, **이미지 타일이 모두 다운로드·렌더링된 시점**과는 다름.
  - 따라서 50ms·80ms 후 또는 `links_changed` 직후에 스왑하면, **다음 파노라마 div는 이미 “활성”이 되었지만, 타일은 아직 로드 중**인 경우가 많고, 그 순간 사용자에게는 **검은 화면(또는 빈 영역)**이 보일 수 있음.

- **스왑이 의미하는 것**
  - doSwap 시 `setVisiblePanoIdx(nextIdx)`로 다음 div가 z-index 상 앞으로 오고, `googleMap.setStreetView(nextPano)`로 해당 파노라마가 “현재 표시 대상”이 됨.
  - 이 순간 **다음 파노라마의 타일이 아직 그려지지 않았다면** → 그대로 **검은 화면**이 노출됨.
  - 이후 타일 로드가 끝나면 장면이 채워지므로, “잠깐 검은 화면 → 다음 장면”으로 느껴짐.

**요약:**  
검은 화면은 **“다음 파노라마의 타일이 완전히 로드·렌더링되기 전에 스왑을 해서, 아직 그려지지 않은 div를 사용자에게 보여주기 때문”**이다. 현재 사용하는 50ms/80ms/links_changed/500ms는 “메타데이터 준비”나 “연결 정보 준비”에 가깝고, “화면에 그림이 다 그려짐”을 보장하지 않는다.

## 3. 검은 화면이 나오지 않게 하기 위한 구체적 방안

(코드는 작성하지 않고, “무엇을 할지”만 제시.)

### 3.1 방안 A: 스왑 전에 “다음 파노라마가 OK인지” 확인 + 추가 지연

- **의도:** 메타데이터만이 아니라, API가 “표시 가능”이라고 알려주는 시점 이후에 한 번 더 기다렸다가 스왑.
- **절차:**
  1. 백그라운드 버퍼(nextPano)에 `setOptions({ pano: panoId, pov: { heading, pitch: 0 }, visible: true })` 적용.
  2. **nextPano**에 대해 `status_changed`를 **1회만** 구독.
  3. `getStatus() === 'OK'`가 되면 리스너 제거, 그리고 **추가로 100~200ms 정도 지연** 후 doSwap 호출.  
     (타일 첫 프레임이 그려질 시간을 주기 위함.)
  4. 위 조건이 일정 시간(예: 1.5초) 안에 오지 않으면 기존처럼 타임아웃으로 doSwap(폴백).
- **효과:** “메타데이터만 OK”인 순간에 스왑하는 비율을 줄이고, 짧은 추가 지연으로 첫 프레임이 그려진 뒤 전환될 가능성을 높여 검은 화면을 줄일 수 있음.
- **트레이드오프:** 전환까지 100~200ms 정도 더 걸릴 수 있음.

---

### 3.2 방안 B: 고정 지연 시간 확대

- **의도:** 현재 50ms / 80ms를 더 늘려, 백그라운드 파노라마가 타일을 받을 시간을 조금 더 줌.
- **절차:**
  - “같은 파노라마·heading만 변경”인 경우: 50ms → **120~150ms**.
  - “연결된 링크”로 전환하는 경우: 80ms → **150~200ms**.
  - 그 외(links_changed 또는 폴백): 500ms 유지 또는 **600ms** 정도로 소폭 증가.
- **효과:** 네트워크가 빠른 환경에서는 타일이 그 전에 로드될 가능성이 커져, 검은 화면이 줄어들 수 있음.
- **트레이드오프:** 전환 체감이 다소 “느려” 보일 수 있고, 느린 환경에서는 여전히 검은 화면이 나올 수 있음.

---

### 3.3 방안 C: 다음 파노라마 미리 로딩(Pre-load) 후 스왑

- **의도:** “지금 바로 쓸 다음” 파노라마를 **미리** 백그라운드 버퍼에 세팅해 두고, 실제로 스왑할 시점에는 이미 로딩이 진행 중이므로 타일이 있을 가능성을 높임.
- **절차:**
  - 시뮬레이션 진행 시 **currentIdx가 N일 때**, 이미 “다음에 보여줄” panoId(예: currentIdx+1 또는 다음 panoData 항목)를 알고 있으면, **그 시점에** 백그라운드 버퍼에만 `setOptions({ pano: nextPanoId, pov: ... })`를 호출해 두고 **스왑은 하지 않음**.
  - 사용자에게 보여줄 전환 시점(예: 다음 인덱스로 넘어갈 때)에는, 이미 백그라운드에서 로딩이 진행된 상태이므로, **방안 A 또는 B와 조합**해 스왑(예: status OK + 100ms 후 스왑).
- **효과:** 스왑 시점에 “방금 pano를 세팅한” 상황을 줄여, 검은 화면이 나올 구간을 줄일 수 있음.
- **트레이드오프:** 로직이 다소 복잡해지고, “다음” 파노라마를 미리 아는 경우(panoData 등)에만 적용 가능.

---

### 3.4 방안 D: 스왑 시 크로스페이드(부드러운 전환)

- **의도:** 순간적으로 “검은 화면”으로 잘리는 대신, **이전 화면 → 다음 화면**으로 짧은 시간 동안 opacity로 전환.
- **절차:**
  - doSwap 시점에 곧바로 z-index만 바꾸지 않고, **현재 보이는 div**는 150~250ms 동안 opacity 1 → 0, **다음 div**는 0 → 1로 서서히 전환.
  - 다음 파노라마가 아직 검은 상태여도 “검은 화면이 서서히 들어오는” 형태가 되어, 스틸사진처럼 **갑자기 검은 화면이 찍혀 나오는** 느낌은 완화될 수 있음.
- **효과:** 검은 화면 자체를 없애지는 못해도, **갑작스러운 검은 스틸사진 같은 느낌**은 줄일 수 있음.
- **트레이드오프:** 여전히 로딩이 늦으면 “검은 화면이 페이드인” 형태로 보일 수 있음.

---

### 3.5 권장 조합

- **1차:** **방안 A**(스왑 전 nextPano `status_changed` → OK 확인 + 100~200ms 추가 지연)를 적용.  
  - 구현 부담이 적고, “메타데이터만 보고 스왑”하는 비율을 줄여 검은 화면을 줄이기 좋음.
- **2차:** **방안 B**를 함께 적용해, “같은 파노·연결된 링크” 전환의 고정 지연을 120~200ms 수준으로 조정.  
  - A와 함께 사용하면, OK 후 추가 지연과 “최소 대기 시간”이 겹쳐 더 안정적.
- **선택:** panoData로 다음 파노라마를 미리 아는 구간이 많다면 **방안 C**를 추가해, “다음” 파노라마를 한 스텝 전에 백그라운드에 세팅해 두고, 스왑은 A+B 조건으로 수행.

## 4. “뒤로 지나가는” 현상 완화(참고)

- 검은 화면 방안과 별개로, “뒤로 지나가는” 느낌을 줄이려면:
  - **방향 필터 실패 시:** `findStreetView` 폴백으로 얻은 파노라마에 대해, **경로 진행 방향(앞쪽)으로의 heading**을 정확히 계산해 적용.  
    (현재도 heading은 경로 기준으로 넣고 있으나, “가장 가까운” pano가 경로 뒤쪽이면 풍경 자체가 후방이므로, 가능하면 **전방 구간의 파노라마를 우선 검색**하는 식의 보강이 도움됨.)
  - **panoData pre-fetch 시:** `findStreetViewInDirection`으로 **전방 ±90°**만 채택하는 정책을 유지하고, 실패 시 **다음 샘플로 재시도**하는 비율을 높이면, 폴백으로 후방 파노라마가 선택되는 경우를 줄일 수 있음.
