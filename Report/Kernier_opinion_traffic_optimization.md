## 1. 총평: 트래픽 우려 및 방향성에 대한 입장

### 1.1 트래픽 우려에 대한 동의

- **“사용자 증가 시 Google API 과금 폭탄”** 가능성은 **실제로 존재**합니다.  
  본인 코드 분석 결과, **Street View getPanorama**와 **Gemini generateContent**가 주행 거리·속도·경로 길이에 비례해 증가하는 구조입니다.  
  Vercel 자체는 정적 호스팅만 하므로 Edge 요청 폭증의 주체는 **Google Maps / Gemini** 호출입니다.
- 다만 **“1명 하루 수천, 100명 수십만”** 수치는 **시나리오(주행 거리, SV 사용 여부, 속도)**에 따라 달라집니다.  
  보수적으로 잡으면: **주행 5km + SV ON** 기준, 기존 구조에서 getPanorama 수백 회·Gemini 수십 회 수준은 충분히 나올 수 있어, **상용 트래픽 시 한도·비용 리스크는 인정**합니다.

### 1.2 PM님 맥락(OSRM, 거리뷰 연속성, 방향 일치)에 대한 동의

- **Google Maps가 모든 지역을 커버하지 못해 OSRM이 필요하다**는 점은 **한국·일부 지역에서 사실**이며, 현재 코드의 Google → OSRM 폴백 설계는 **합리적**입니다.
- **“주행과 동기화된 거리뷰 + 끊김 없음 + 방향 일치”**는 시뮬레이터의 **핵심 가치**입니다.  
  이를 위해 **가장 가까운 거리뷰 + 3단계 검색(50m → look-ahead 5 → 100m) + 이중 버퍼링**으로 설계된 현재 로직은 **기능적 완성도를 우선한 선택**으로 보입니다.
- 따라서 **“기능을 줄여서 트래픽을 낮추는 방식”은 반대**하며, **“구조 최적화(사전 준비 + 로컬 처리)”** 방향에 **전적으로 동의**합니다.

## 2. 제안된 전략에 대한 세부 의견

### 2.1 구간 기반 처리 (좌표 → 거리 기준)

- **의견: 채택 권장.**  
  현재도 `densifiedPath`는 2m 단위이고, getPanorama는 **“15m 이격 시”**에만 호출되므로 완전한 “조금만 움직여도 호출”은 아니나, **위치 변화 = 조건 충족 시 API** 구조는 그대로입니다.
- **경로를 100m(또는 50m) 세그먼트로 나누고, “현재 거리 → 세그먼트 인덱스 → 미리 확보한 데이터만 사용”**으로 가면 **주행 중 API 호출을 구조적으로 0으로 만드는 데 직결**됩니다.
- OSRM 사용 시에도 **path는 이미 확정**되므로, Google/OSRM 구분 없이 **동일 path 기준**으로 세그먼트화·프리패칭 적용 가능합니다.

### 2.2 Street View 사전 캐싱(프리패칭)

- **의견: 최우선 적용 대상.**  
  트래픽 분석상 **가장 많이 불리는 부분**이 getPanorama입니다.
- **경로 확정 후 50~100m 간격으로 PanoID·Heading 미리 수집**하면, **RUNNING 중에는 getPanorama 0회**로 만들 수 있습니다.  
  “스트리밍 → 재생” 비유는 적절합니다.
- **주의점:**
  - **경로 길이에 비례한 초기 호출**이 한꺼번에 발생합니다(예: 10km → 100~200회).  
    Google Maps API **할당량/초당 제한**에 걸리지 않도록, 호출 간 **짧은 딜레이(예: 50~100ms)** 또는 **배치 크기 제한 후 나눠 호출**을 권장합니다.
  - **Street View 없는 구간**(터널, 산길): 현재도 3단계 검색으로 “건너뛰기”를 하고 있으므로, 프리패칭 시에도 **해당 구간은 빈 슬롯 또는 다음 유효 PanoID로 대체**하는 전략이 필요합니다.
  - **“Preparing Street View...”** 동안 대기 시간이 길어질 수 있음(10km면 수십 초). **진행률 표시(예: N/100 스캔)**를 넣어 주는 것을 권장합니다.

### 2.3 Heading(방향) 계산 분리

- **의견: 이미 충족.**  
  코드에서 **방향은 이미 `google.maps.geometry.spherical.computeHeading`으로 로컬 계산**하고 있으며, **방향을 위한 추가 서버 요청은 없습니다.**  
  문서화·정리만 해도 되고, “Zero API Heading”은 현재 구조를 유지하면 됩니다.

### 2.4 Throttle / Debounce

- **의견: panTo 스로틀(1초 1회 등)은 채택 권장.**  
  스트리트뷰 전체화면 시 `panTo`가 매 스텝마다 호출되면 불필요한 렌더링·타일 로딩이 발생할 수 있으므로, **1초 1회 또는 마커가 뷰 밖으로 나갈 때만** 호출하는 방식이 적절합니다.
- **API 호출 자체**는 Throttle보다 **“구간/캐시 기반으로 호출 제거”**가 우선입니다.  
  구간·프리패칭 적용 후에도 남는 호출이 있다면 그때 Throttle을 보완으로 적용하면 됩니다.

### 2.5 클라이언트 캐시(IndexedDB / LocalStorage)

- **의견: 채택 권장.**  
  **My Routes**에서 경로 재주행 시 **path, elevation, panoData**를 복원하면 Directions·Elevation·Street View 메타 **재호출을 전면 제거**할 수 있습니다.
- **보완:**  
  - **저장 용량**: 경로당 panoData 크기·개수 제한(예: 최근 5개 경로, 또는 N MB).  
  - **식별자**: origin+destination+waypoints 해시 등으로 키 생성.  
  - **만료**: 오래된 항목 삭제 정책 권장.

### 2.6 상태머신(PREPARING / RUNNING)

- **의견: 채택 권장.**  
  **PREPARING(API 허용) / RUNNING(캐시만 사용)**로 구분하면 **트래픽이 예측 가능**해지고, “주행 중 수천 건 요청”을 **구조적으로 0에 수렴**시킬 수 있습니다.  
  구현은 **플래그(isPreparing / isRunning)**만으로도 가능하며, 필요 시 상태를 확장해도 됩니다.

## 3. AI 코칭 “방안 2: 예측 코칭”에 대한 의견

- **의견: 채택 권장.**  
  현재 **21스텝마다** Gemini 호출하는 구조보다, **한 번에 500m~1km 구간 코칭을 받아 validUntilIndex까지 재생**하는 방식이 **호출 횟수·토큰을 크게 줄입니다.**
- **고려할 점:**
  1. **구간 이질성**: 한 구간 안에 평지→급경사가 섞이면, “한 번에 받은 코칭”이 구간 후반과 안 맞을 수 있음.  
     → **구간 길이(500m vs 1km)** 또는 **경사 변화율이 큰 지점에서 구간 분할**을 설계 단계에서 정하면 됩니다.
  2. **일시정지 후 재개**: 구간 중간부터 재개 시 `validUntilIndex`와의 정합성(어떤 팁을 보여줄지) 규칙을 명확히 할 필요가 있습니다.
  3. **Gemini 응답 구조**: “다음 N미터에 대한 코칭 시퀀스”(여러 팁 vs 하나의 긴 안내)를 **스키마로 고정**하고, 클라이언트에서 `cachedCoaching[]`에 **validUntilIndex와 함께** 저장하는 설계가 필요합니다.

위를 전제로 하면 **기능 수준을 유지하면서 트래픽을 획기적으로 줄이는 데 적합**합니다.

## 4. 단계적 세부 실행 계획서에 대한 의견

### 4.1 1단계: 데이터 스키마 및 상태 관리

- **RouteInfo에 panoData[], cachedCoaching[] 추가**: 적절합니다.  
  **CoachingData에 validUntilIndex(또는 유효 구간 인덱스)** 추가도 예측 코칭과 일치합니다.
- **상태머신(IDLE / PREPARING / RUNNING)**: 플래그로 구현 가능하며, PREPARING 중에는 “경로·고도·SV 메타·코칭 배치” 수집만 허용하고, RUNNING 중에는 API 금지로 두는 식이면 됩니다.

### 4.2 2단계: 스트리트뷰 배치 프리패칭

- **경로 완료 직후 100m(또는 50m) 간격 스캔**: 방향성 동의합니다.
- **실패 처리**: 해당 구간에 Street View가 없으면 **빈 슬롯 또는 다음 유효 PanoID 참조**로 보간하는 규칙을 계획서에 명시할 것을 권장합니다.
- **UI**: “Preparing Street View...” + **진행률(N/M)** 표시를 계획에 포함하면, 긴 경로에서도 대기 체감이 줄어듭니다.
- **path와 panoData 매핑**: path는 2m 단위 densifiedPath, panoData는 100m 간격이므로 **“현재 path 인덱스 → 거리 → 가장 가까운 panoData 포인트”** 또는 **거리 구간으로 이진 탐색** 등 매핑 규칙을 4단계와 함께 명확히 할 필요가 있습니다.

### 4.3 3단계: AI 코칭 예측 코칭(방안 2)

- **getAdvancedCoaching 시그니처**: “현재 위치 + 향후 500m~1km 구간 전체 고도 프로필”을 한 번에 넘기고, **해당 구간을 관통하는 코칭 시퀀스(팁 + validUntilIndex)**를 받는 형태로 정리하면 됩니다.
- **구간 경계**: 한 구간이 끝나기 직전(예: validUntilIndex - 50 스텝)에 **다음 구간 코칭을 미리 요청**해 두면, 끊김 없이 이어질 수 있습니다(선택 사항).

### 4.4 4단계: 시뮬레이션 루프 Zero-Traffic 전환

- **거리뷰**: 실시간 findStreetView 제거 후 **panoData에서 현재 인덱스에 해당하는 PanoID·Heading만 사용**하는 방향 적절합니다.
- **인덱스↔거리↔panoData**: 2단계에서 정의한 **path 인덱스–거리–panoData 매핑**을 그대로 사용하면 됩니다.
- **panTo 스로틀**: 1초 1회 또는 마커가 뷰 밖으로 나갈 때만 호출하는 것을 계획에 포함하는 것을 권장합니다.

### 4.5 5단계: 클라이언트 캐시

- **My Routes 복원 시 path, elevation, panoData 복원**: 동의합니다.  
  **캐시 키(경로 식별자), 용량 제한, 만료 정책**을 실행 계획에 포함할 것을 권장합니다.

## 5. 리스크 및 보완 제안

| 항목 | 내용 | 보완 제안 |
|------|------|-----------|
| **Google API 할당량** | 프리패칭 시 순간적으로 많은 getPanorama 호출 가능 | 호출 간 50~100ms 딜레이 또는 배치 크기 제한 후 분할 호출 |

| **캐시 용량** | panoData·elevation 저장량 증가 | 경로당/전체 용량 상한, LRU 등 만료 정책 |

- **실행 계획서**의 5단계 구성과 **AI 코칭 방안 2(예측 코칭)** 채택은 **현재 코드와 설계 제안서와 정합**하며, 위 리스크만 계획에 반영하면 **승인 후 단계별 구현**에 들어가도 무방하다는 것이 커니어의 의견입니다.
