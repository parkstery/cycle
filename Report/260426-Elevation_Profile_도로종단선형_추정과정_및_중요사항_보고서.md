# 260426-Elevation Profile 도로 종단 선형 유사화 추정 과정 및 중요 사항 보고서

## 1. 목적과 용어

### 1.1 목적

실내 사이클 앱에서 **경로에 따른 표고 프로필**이 가능한 한 **실제 도로의 종단 선형(longitudinal profile)** 과 비슷하게 느껴지도록 하고, 그 결과로 **고도 차트**와 **코칭(경사·저항 밴드)** 이 서로 어긋나지 않게 하는 것이 목표였다.

### 1.2 “도로 종단 선형”과 앱이 갖는 데이터의 차이

- **도로 종단 선형(이상)**: 차로면(deck)을 따라 이어지는 설계·시공 기준의 종단 곡선. 교량·터널·비탈면에서 DEM(지표면)과 **체계적으로 다를 수 있다**.
- **앱이 실제로 갖는 것**: OSRM 등으로 얻은 **폴리라인 상의 샘플점**에 대해, Open-Elevation 등으로 얻은 **DEM 기반 고도**. 즉 **“지표/지형 격자를 경로에 투영한 값”**에 가깝고, **도로 구조물의 선형 고도**를 직접 측정한 값은 아니다.

따라서 본 프로젝트에서 한 일은 **물리적 도로 설계도를 복원**하는 것이 아니라, **DEM 기반 샘플을 도로 체감에 가깝게 완화·추정**하는 **휴리스틱 파이프라인**을 두는 것이다.

---

## 2. 추정 과정의 연혁(요약)

아래는 논의·구현이 진행된 순서를 기능 관점으로 요약한 것이다.

1. **초기**: 샘플 간 고도 차이로부터 단순 경사(%)를 구해 코칭에 사용. DEM 노이즈·교량 구간의 급격한 U자 등이 그대로 반영됨.
2. **스무딩**: `smoothElevations`(이동 평균 등)로 **고도 시계열** 자체를 완화. 스파이크는 줄지만, **구간 경사의 물리적 일관성**은 별도로 보장하지 않음.
3. **“도로 추정” 경사(slope)**: DEM을 따라가는 샘플 위에서, **거리 기반 가변 창**·**저역 통과**·**경사 변화율 제한**·**교량형 패턴 완화** 등을 적용해 **코칭용 대표 경사**를 계산. (`estimateRoadSlope` 쪽 로직이 `services/roadElevation.ts`로 정리됨.)
4. **전 프로필 보정**: 코칭만이 아니라 **차트에 쓰는 `route.elevation` 자체**를 같은 철학으로 한 번 더 다듬어, **차트와 코칭이 같은 배열**을 보도록 **단일 소스화**. (`applyRoadElevationModel`)
5. **외부 “도로 고도 엔진” 검토(폐기)**: Valhalla `elevation_interval` 등 **라우터 측 표고**를 시험했으나, 효과·운영(키·CORS·네이티브 URL) 대비 **도입 방향은 폐기**로 결정됨. 본 보고서의 기준 구현은 **현재 `dev2` 기준 Open-Elevation + `roadElevation` 파이프라인**이다.

## 3. 현재 구현의 핵심 구조

### 3.1 단일 소스: `route.elevation`

- 경로가 확정·복원·self-heal 등으로 고도 배열이 만들어진 뒤, **`applyRoadElevationModel`** 을 거쳐 **`route.elevation`** 에 반영한다.
- **고도 차트**와 **코칭** 모두 이 **`route.elevation`** 을 입력으로 삼는다.  
  → “차트는 raw DEM, 코칭만 보정” 같은 **이중 체계를 피한다**는 것이 중요한 설계 결정이다.

### 3.2 파이프라인 순서(대표)

1. Open-Elevation(또는 동등 API)으로 **경로 샘플별 고도** 수집.
2. **`smoothElevations`** 로 고도 값 1차 완화(이동 평균).
3. **`applyRoadElevationModel`** 로 **도로에 가깝다고 가정한 종단 형태**로 보정한 고도로 치환.

코칭 슬라이스에서는 **`estimateRoadSlope`** 가 위에서 만든 **같은 종류의 “도로형” 고도 해석**을 사용해 경사(%)를 구하고, 이를 **R1~R8** 저항 밴드로 매핑한다. (`services/aiCoach.ts`)

### 3.3 `roadElevation.ts`에서의 주요 아이디어

| 구분 | 내용 |
|------|------|
| **거리 축** | 샘플을 **누적 거리(m)** 로 정렬해 “종단 방향” 상에서 연산한다. |
| **가변 스무딩 창** | 구간 길이에 따라 **창 길이(m)** 를 늘리는 등, 긴 구간에서 과도한 미세 요동을 줄인다. |
| **도로형 고도** | 창 내 평균 고도 등으로 **“도로면에 가깝다고 가정한 고도”** 시리즈를 만든다. |
| **창 기반 경사** | 인접 한 점이 아니라 **창 구간의 고도차/거리**로 경사를 잡아 DEM 스파이크에 덜 흔들리게 한다. |
| **양방향 저역 통과** | 경사 시퀀스에 **앞·뒤 방향 스무딩**을 결합해 위상 지연을 완화한다. |
| **경사 변화율 제한** | 샘플 간 거리에 비례해 **구간당 경사 변화 상한**을 두어 비현실적인 급변을 줄인다. |
| **교량형 패턴(코칭)** | 양 끝 고도는 비슷한데 중앙이 크게 꺼지는 등 **DEM “U자 골짜기”** 에 가까운 패턴이면, **대표 경사에 가중을 줄여** 과도한 내리막 코칭을 완화한다. |
| **장교량형(프로필)** | 매우 긴 구간에서 위와 유사한 패턴이면, **끝점을 잇는 직선(deck)** 쪽으로 **하방만 블렌딩**해 차트 상 골이 과하게 깊어 보이는 현상을 줄인다. |

상수 이름으로는 `ROAD_SMOOTH_WINDOW_M`, `ROAD_SLOPE_LOW_PASS_ALPHA`, `ROAD_SLOPE_DELTA_LIMIT_PER_50M`, `BRIDGE_PATTERN_*` 등이 코드에 직접 드러나 있어 튜닝 시 참고할 수 있다.

### 3.4 코칭 갱신과 세그먼트 길이

- 예측 코칭에서 **세그먼트 크기(경로 인덱스 기준)** 를 줄여, **같은 R이 너무 오래 유지**되는 문제를 완화했다.  
  → “지금 달리는 국면”과 화면의 R이 어긋나는 체감을 줄이기 위한 **UX 파라미터**이며, 종단 추정 자체와는 별도 축의 조정이다.

## 4. 한계와 오해하기 쉬운 점

1. **데이터의 본질**: DEM은 **지형면**에 가깝다. **교량·입체교차·터널 포털** 등에서 실제 차로 고도와 **구조적으로 다를 수 있으며**, 특히 **긴 교량**에서는 체감 차이가 남을 수 있다.
2. **OSRM 기하 vs 고도 샘플**: 경로 기하는 OSRM, 고도는 샘플링·API 해상도의 제약이 있다. **“같은 선상의 진짜 deck 고도”** 를 보장하지는 않는다.
3. **휴리스틱의 상 trade-off**: 교량형 패턴을 더 강하게 누르면 **실제 오르막/내리막**까지 눌릴 위험이 있다. 상수는 **현장 피드백과 로그**를 보며 조정하는 것이 안전하다.
4. **외부 라우터 표고(Valhalla 등)**: 이론적으로는 구조물 선형에 유리할 수 있으나, 본 프로젝트에서는 **도입을 폐기**했고, 현재 **운영 기준선은 Open-Elevation + `roadElevation`** 이다.

---

## 5. 후속 작업 시 권장 체크리스트

- **`route.elevation` 단일 소스**를 깨지 않을 것(차트 전용 raw, 코칭 전용 보정 등으로 **이중화하지 않기**).
- 고도 파이프라인을 바꿀 때는 **`smoothElevations` → `applyRoadElevationModel` 순서**와 **`estimateRoadSlope`와의 일관성**을 함께 검토할 것.
- 상수·창 길이·교량 판별 임계값을 바꿀 때는 **짧은 교량 / 긴 교량 / 터널 인근 / 해안 도로** 등 **회귀 시나리오**를 정해 두고 비교할 것.
- Android 빌드에서는 **Google Maps·Elevation API 키** 등 **지도 자체가 뜨는 전제**가 먼저이며, 표고는 그 다음 레이어다.
