# 자문 최종 정리안에 대한 의견
2026-02-06
**대상**: “안 보이는 문제 해결 + 비용 통제” 최종 정리안  
**의견 요지**: 원칙·구조·효과는 대체로 타당하고, 세부 수치와 단계 적용 순서만 실사용 데이터로 조정하는 편이 좋겠다는 입장입니다.

---

## 1. 문제 정의와 원칙에 대한 동의

### 1.1 본질 진단

- **“파노가 있음에도 조건 때문에 탈락”**  
  현재는 반경·방향을 동시에 엄격히 걸어서, 실제로는 근처에 파노가 있어도 한 번에 탈락하는 구조가 맞습니다.  
  반경 200m로 완화한 최근 수정으로 일부 개선되겠지만, **단일 조건(통과/탈락)** 자체는 한계가 있다는 점에 동의합니다.

- **“실패 → 재검색 → API 폭증”**  
  주행 중 실시간 검색·폴백이 남아 있으면, 구간이 길어질수록 호출이 불확정하게 늘어날 수 있다는 지적도 맞습니다.  
  이미 “주행 중 시도 횟수 상한·반경 200m·ZERO_RESULTS 시 DEFAULT 생략” 등으로 완화했지만, **원칙적으로 “주행 중 API = 0”**으로 가는 방향은 비용·예측 가능성 측면에서 타당합니다.

### 1.2 최상위 원칙

- **원칙 1. 주행 중 새로 찾지 않는다**  
  → 비용 통제와 “끊김·검은 화면” 감소 모두에 직결되므로 **전적으로 동의**합니다.

- **원칙 2. 찾을 때는 여러 후보 중 최적을 고른다**  
  → “있는데 안 나오는 문제”를 줄이는 핵심입니다.  
  단일 조건(반경·heading) 통과/탈락 대신 **후보 수집 + 점수 선택**으로 바꾸는 방향에 **동의**합니다.

- **원칙 3. 못 찾으면 끈다 (OFF)**  
  → 무한 폴백·재시도를 막고, 사용자에게 “이 구간은 거리뷰 없음”으로 명확히 알리는 측면에서 **동의**합니다.  
  다만 “끈다”가 **구간 단위**인지 **전체 Street View 비활성**인지는 UX와 정책 선택 사항이라, 자문안 10항 “coverage 70% 미만 → StreetView 비활성”처럼 **정량 기준**을 두는 쪽을 권장합니다.

## 2. 제안 구조에 대한 의견

### 2.1 Multi-pass + Scoring (1단계)

- **다단계 탐색(25m ±20° → 45m ±40° → 70m 제한 없음)**  
  - “먼저 가까운·방향 맞는 것, 없으면 넓게”라는 순서는 합리적입니다.  
  - 다만 **25m가 너무 좁아서** 도로–촬영 위치 오차가 있는 구간에서는 1단계에서 대부분 탈락할 수 있습니다.  
  - **의견**: 1단계를 40~50m, 2단계 80m, 3단계 120~150m 등으로 조금 더 넓게 두고, 실제 경로 데이터로 “어느 단계에서 대부분 수집되는지” 한 번 보는 것을 제안합니다.  
  - 반경을 넓히면 후보 수가 늘어나 비용이 올라가므로, **densifiedPath 완화(10~15m)** 와 함께 총 호출 수를 계산해 보는 것이 좋습니다.

- **점수 기반 선택 (거리 + 방향)**  
  - 통과/탈락 대신 **score = 0.6×(1 - d/maxD) + 0.4×(1 - diff/90)** 식으로 “가장 나은 하나”를 고르는 방식은 **방향이 맞습니다**.  
  - **의견**:  
    - 가중치(0.6/0.4)와 maxD, diff 분모(90 등)는 **실제 경로·지역 샘플**로 조정하는 것이 좋고,  
    - “실내·상가”를 걸러내려면 아래 2단계(메타데이터/필터)와 **동일 후보 집합**에 적용하는 구조가 맞습니다.

### 2.2 실내 파노 차단 (2단계)

- **heading 대신 description/copyright/source, tilt 필터**  
  - “heading으로만 실내 차단”이 한계가 있다는 진단에 **동의**합니다.  
  - **의견**:  
    - **메타데이터 필터**는 Google Street View API가 **description, copyright** 등을 어느 수준까지 제공하는지 스펙 확인이 필요합니다.  
    - 제공 필드가 제한적이면 “키워드(Shop/Indoor/Business) 제외”는 **부분적으로만** 적용 가능할 수 있어, 우선은 **tilt/pitch 이상치 제외**를 1차로 두고, 메타데이터는 가능한 범위에서 보완하는 순서를 제안합니다.  
    - 실내 구간이 많은 코스는 어차피 “coverage 낮음 → 비활성 또는 안내”로 처리할 수 있으므로, 필터는 **과도한 실내 노출을 줄이는 수준**으로 두는 것이 현실적입니다.

### 2.3 Prefetch 강화 (3단계)

- **densifiedPath 2m → 10~15m**  
  - 호출 수를 **5~7배 줄인다**는 방향에 **동의**합니다.  
  - **의견**:  
    - 2m는 거리뷰 전환 부드러움을 위해 쓰였을 가능성이 있으므로, **10m로 완화** 시 주행 시 화면 전환 주기가 얼마나 굵어지는지 한 번 확인하는 것이 좋습니다.  
    - 7m와 10m, 15m를 짧은 구간으로 A/B 체감 테스트해 보면, “비용 vs 부드러움” 타협점을 정할 수 있습니다.

- **prefetch 거리 200m → 400~600m**  
  - 초기 로딩만으로도 “바로 끊김”을 줄이는 데 **효과적**입니다.  
  - **의견**:  
    - 400~600m를 **한 번에** 하면 “Preparing…” 시간이 길어질 수 있으므로,  
    - 자문안의 **슬라이딩 prefetch(남은 거리 < 200m → 다음 500m)** 와 조합해,  
    - “초기 300m + 주행 중 200m 남을 때마다 다음 400m”처럼 **단계적 확장**이 현실적입니다.

- **슬라이딩 prefetch**  
  - “주행 중 API = 0”을 유지하면서 구간을 이어 붙이는 방식으로 **구조 자체에 동의**합니다.  
  - 이미 현재 코드에 “캐시 끝 근처에서 다음 200m 온디맨드”가 있으므로, **반경·시도 제한·점수 선택**만 정리하고, “다음 Nm”을 400~500m로 키우는 식의 확장이 자연스럽습니다.

### 2.4 Fallback 완전 제거 (4단계)

- **“캐시에 없으면 setPanoramaView(pos, heading) 호출하지 말고, disableStreetView() 또는 거리뷰 없음 표시”**  
  - 비용 폭탄 차단과 “예측 가능한 동작” 측면에서 **전적으로 동의**합니다.  
  - 이미 “실시간 시도 상한 3회, ZERO_RESULTS 시 DEFAULT 생략”을 넣었지만, **원칙적으로 주행 중 getPanorama 호출 자체를 제거**하는 것이 자문안과 일치합니다.

### 2.5 Prefetch 단계에서 “후보 → 1개 확정 → 저장” (5단계)

- **저장 형식 { index, panoId, heading, isUser }**  
  - 주행 중에는 **캐시 lookup만** 하면 되므로 **동의**합니다.  
  - 현재도 panoData에 비슷한 형태를 쓰고 있으므로, **후보 수집 + 점수 선택**만 prefetch 파이프라인에 넣으면, 저장 구조는 자연스럽게 이 형태로 정리될 수 있습니다.

## 3. 우선 적용 순서에 대한 제안

자문안이 “설계 원칙 → 구조 → 구현 포인트”로 잘 정리되어 있으나, **구현 부담과 효과**를 고려하면 아래 순서를 제안합니다.

1. **원칙 1·3 확정**  
   - 주행 중 API 호출 제거(실시간 fallback 제거).  
   - 캐시에 없으면 거리뷰 끄기 또는 “이 구간 거리뷰 없음” 표시.  
   → 비용·예측 가능성 확보의 **기반**이 됩니다.

2. **Prefetch에서 “후보 수집 + 점수 선택” 도입**  
   - 다단계 반경/각도는 **우선 2단계**(예: 50m ±40°, 120m 제한 없음)로 단순화해 적용하고,  
   - 통과/탈락 대신 **점수 기반 1개 선택**만 먼저 넣어도 “있는데 안 나오는 문제”가 상당 부분 줄어듭니다.

3. **densifiedPath 완화(10m) + prefetch 구간 확대(초기 300m, 슬라이딩 400m)**  
   - 호출 수 감소와 끊김 감소를 동시에 노립니다.

4. **실내 필터(tilt, 가능 시 메타데이터)**  
   - API 제공 범위 확인 후, tilt 이상치 제거를 먼저, 메타데이터는 보조로 적용합니다.

5. **coverage 70% 미만 시 Street View 비활성 + 사용자 안내**  
   - 품질·비용 제한과 UX를 함께 만족시키는 **운영 전략**으로 적용하는 것을 권장합니다.

---

## 4. 요약

- **자문안의 방향성(원칙 1·2·3, prefetch 확정·주행 중 API 0, fallback 제거, 슬라이딩 캐시)** 에는 **전반적으로 동의**합니다.  
- **Multi-pass 반경·각도 수치**는 실제 데이터로 한 번 조정하고, **점수 선택**을 먼저 도입하는 것이 효율적입니다.  
- **실내 차단**은 API 스펙 확인 후 tilt 위주로 적용하고, 메타데이터는 보완 수준으로 두는 것을 제안합니다.  
- **“찾을 땐 똑똑하게, 쓸 땐 조용하게”**라는 한 줄 요약은 그대로 수용해도 좋다고 봅니다.

이상이 자문 최종 정리안에 대한 의견입니다.
