# 경로 탐색 시 처음 200m 구간 스트리트뷰 로드 로직 설명

## 1. 로직 요약

경로 탐색(OSRM + 표고 계산)이 끝난 직후, **출발점부터 200m 구간**만 먼저 스트리트뷰 파노라마 메타데이터(panoId, heading 등)를 **미리 수집**해 `route.panoData`에 넣습니다.  
이후 주행 중에는 이 캐시를 쓰고, 200m 끝에 가까워지면 **그 다음 200m 구간을 온디맨드**로 추가 수집합니다.

---

## 2. 동작 흐름 (경로 탐색 직후)

### 2.1 호출 위치

경로가 성공적으로 세팅된 직후, `calculateRoute` 내부에서 다음 비동기 블록이 실행됩니다.

```ts
// Progressive loading: pre-fetch first 200m (10m interval) for continuous display; rest loaded on-demand
(async () => {
  setAppPhase('PREPARING');
  setPreparingProgress({ k: 0, n: 1 });
  const panoData = await preFetchStreetViewData(
    densifiedPath,
    (k, n) => setPreparingProgress({ k, n }),
    { maxDistanceM: 200, intervalM: 7 }
  );
  setPreparingProgress(null);
  setRoute((prev) => (prev ? { ...prev, panoData } : null));
  setAppPhase('IDLE');
  // ... autoStart 시 카운트다운·시뮬레이션 시작 등
})();
```

- **PREPARING** 동안만 스트리트뷰 API를 쓰고, UI에는 "Preparing Street View... (k/n)" 진행률이 표시됩니다.
- **maxDistanceM: 200** → 경로 상 **0m ~ 200m** 구간만 프리페치 대상.
- **intervalM: 7** → 약 **7m 간격**으로 샘플 지점을 잡고, 각 지점에서 파노라마를 한 번씩 조회합니다.

---

## 3. `preFetchStreetViewData` 상세 로직

### 3.1 구간·샘플 결정

1. **누적 거리 배열 `cumDist`**  
   `path`의 점 간 거리를 합쳐 `cumDist[i]` = path[0] ~ path[i]까지의 거리(m)로 둡니다.

2. **샘플 인덱스 계산**  
   `fromDistanceM`(기본 0)부터 `maxDistanceM`(여기서는 200)까지 **intervalM(7m) 간격**으로 거리 `d`를 두고,  
   `cumDist[i + 1] < d`인 동안 `i`를 증가시켜, 각 `d`에 대응하는 **path 인덱스**를 구합니다.

   - 예: 0m, 7m, 14m, …, 196m → 대략 **29개** 샘플 지점(200m 구간, 7m 간격).

3. **각 샘플 지점에서 할 일**  
   해당 path 점 위치에서 Google Street View Service로 **그 근처의 파노라마**를 찾고,  
   **주행 방향과 비슷한 방향**(전방 ±110° 이내)의 파노라마만 채택합니다.

### 3.2 파노라마 찾기 (방향 필터 + 폴백)

각 샘플 지점 `pathPoint`에 대해:

1. **findStreetViewInDirection**  
   - 반경 30m → 실패 시 20m → 15m 순으로 시도.  
   - 찾은 파노라마가 **주행 방향(pathPoint → pathNext)** 과 **±110°** 이내인지 확인.  
   - 조건을 만족하면 `{ pathIndex, panoId, location, heading, isUserPhoto }` 형태로 저장.

2. **방향 필터 실패 시 폴백**  
   - 방향 조건을 만족하는 파노라마가 없으면 **findStreetView**로 같은 지점 근처(반경 50m) 파노라마만 찾아서라도 추가.  
   - “연속 디스플레이 우선”: 해당 구간에 파노라마가 있으면 방향과 무관하게 넣어, 구간이 빠지지 않도록 함.

3. **API 부하 완화**  
   - 샘플 간 **80ms 지연** (`await new Promise(r => setTimeout(r, 80))`)으로 연속 호출을 완화.

4. **진행률**  
   - 매 샘플 처리 후 `onProgress(k + 1, n)` 호출 → 화면에 "Preparing Street View... (k/n)" 갱신.

결과 배열 `panoData`가 `route.panoData`로 저장되고, 주행 시 **현재 path 인덱스에 맞는 panoData 항목**을 `getPanoDataForIndex`로 찾아 파노라마를 전환합니다.

---

## 4. 주행 중 사용 방식

- **캐시 사용**  
  `route.panoData`가 있으면, 현재 주행 위치(path index)에 해당하는 pano 항목을 찾아 **panoId + heading**으로만 전환합니다.  
  이때는 **Street View API를 다시 부르지 않고** 이미 받아 둔 메타데이터만 사용합니다.

- **온디맨드 추가 로드**  
  주행 인덱스가 **캐시된 마지막 pano의 pathIndex - 150** 근처에 오면,  
  “캐시 끝 구간에 다가왔다”고 보고, **그 다음 200m 구간**을 같은 `preFetchStreetViewData`로 요청합니다.  
  - `fromDistanceM` = 마지막 pano 위치 + 10m  
  - `maxDistanceM` = 그 위치 + 200m (단, 경로 총 길이를 넘지 않도록)  
  - `isSegmentFetchingRef`로 동시에 여러 세그먼트 요청이 나가지 않도록 한 번에 하나만 실행.

즉, **처음 200m는 경로 탐색 직후**, **그 다음 200m는 주행 중 필요할 때** 로드하는 **프로그레시브 로딩** 구조입니다.

---

## 5. “처음 200m만” 이렇게 구성한 이유

### 5.1 빠른 주행 시작 (체감 대기 시간 감소)

- 경로 전체(수 km~수십 km)의 스트리트뷰를 다 받고 나서야 Go를 누르면, 사용자는 오래 기다리게 됨.  
- **200m만** 미리 받으면, 대략 7m 간격 29점 수준이라 수 초 내에 끝나고, **바로 주행(Go)을 시작**할 수 있음.  
- 200m는 저속(~20km/h)으로도 수십 초 분량이라, “시작하자마자 끊김 없이 보여준다”는 목표에 맞는 구간 길이.

### 5.2 API 호출 수·비용·정책

- Street View API는 호출당 비용·정책 제한이 있음.  
- 전체 경로를 한 번에 다 조회하면 호출 수가 크게 늘고, 사용자가 “경로만 보고 Go는 안 누르는” 경우에도 전부 호출해 버리는 비효율이 있음.  
- **200m만** 프리페치하면 호출 수를 고정된 작은 단위로 잘라서, “일단 시작 구간만 확보”하고 나머지는 **정말 주행할 때만** 추가 로드할 수 있음.

### 5.3 주행 중 끊김 방지 (프로그레시브 + 온디맨드)

- 처음 200m를 미리 받아 두었기 때문에, **시작 직후에는 API 없이** 캐시만으로 화면 전환이 가능함.  
- 200m 끝 근처에 도달하기 전에 “다음 200m”를 요청해 두므로, 사용자가 “끝까지 갔는데 다음 화면이 안 나온다”는 상황을 줄일 수 있음.  
- 한 번에 하나의 “다음 200m”만 요청하도록(throttle) 해서, 주행 중 API 호출이 폭주하지 않도록 함.

### 5.4 7m 간격(intervalM: 7)을 쓰는 이유

- **너무 촘촘하면** (예: 2m마다) 샘플 수가 늘어나 API 호출과 PREPARING 시간이 커짐.  
- **너무 성기면** (예: 30m마다) 같은 파노라마가 길게 이어져, 주행 시 화면 전환이 덜 부드러울 수 있음.  
- **7m**은 “몇 초에 한 번 꼴로 파노라마가 바뀌는” 수준으로, 체감상 자연스러우면서도 200m 구간 샘플 수(~29개)를 적당히 유지하는 타협값으로 보임.  
- (경로는 이미 segment 2m 단위로 densified 되어 있어, 7m 간격은 path 상 여러 점 중 일부만 골라 쓰는 것과 같음.)

---

## 6. 정리

| 항목 | 내용 |
|------|------|
| **무엇을** | 경로 상 **0~200m 구간**의 스트리트뷰 파노라마 메타데이터(panoId, heading 등) |
| **언제** | 경로 탐색(OSRM·표고) 완료 직후, PREPARING 단계에서 한 번 |
| **어떻게** | 7m 간격 샘플 지점에서 `findStreetViewInDirection`(방향 필터) → 실패 시 `findStreetView` 폴백, 80ms 간격으로 API 호출 |
| **왜 200m** | 주행 즉시 시작 가능 + API 호출·비용 절감 + 나머지는 주행 중 온디맨드로 이어서 로드(프로그레시브 로딩) |
| **이후** | 주행 중에는 이 캐시만 사용하다가, 캐시 끝 근처에서 다음 200m 구간을 같은 방식으로 추가 요청 |

이 구조로 “경로 탐색 시 처음 200m 구간의 스트리트뷰를 로드하는 로직”이 동작하며, 위와 같은 이유로 그렇게 구성되어 있습니다.
