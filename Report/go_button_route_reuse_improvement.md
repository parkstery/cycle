# Go 버튼 클릭 시 경로 재계산 중복 제거 — 시니어 개선 방안

**작성일:** 2025-01-31  
**대상:** PM  
**목적:** 경로탐색으로 이미 계산된 경로가 있을 때, Go 버튼 클릭으로 인한 불필요한 재계산·서버 트래픽 제거 방안 제시 (코드 미작성)

---

## 1. 문제 정의

- **경로탐색** 버튼: 경로만 계산하고 시뮬레이션은 시작하지 않음.
- **Go** 버튼: 경로 계산 후 시뮬레이션 자동 시작.

사용자 시나리오:

1. 출발·도착 입력 후 **경로탐색** 클릭 → Directions API·Elevation API 호출 → 경로·고도·거리/시간 표시.
2. 사용자가 거리/시간을 확인한 뒤 **Go** 클릭 → 현재 구현에서는 **동일한 경로를 다시** Directions·Elevation로 계산한 뒤 시뮬레이션 시작.

이때 **동일한 출발·도착·경유지·이동수단**에 대해 API를 두 번 호출하게 되어, 기능 중복과 서버 트래픽(Google Directions, Elevation, 이후 PREPARING 단계의 Street View 등)이 발생함.

---

## 2. 개선 방향 (원칙)

- **경로탐색**으로 계산한 결과는 “현재 표시된 경로”로 간주하고, **Go** 클릭 시 **입력값이 그대로라면** 재계산 없이 **기존 경로로 시뮬레이션만 시작**한다.
- 입력값(출발·도착·경유지·이동수단)이 **변경된 경우**에만 Go 클릭 시 경로를 다시 계산한다.

---

## 3. 구체적 개선 방안

### 3.1 “마지막 경로 요청 파라미터” 보관

- **목적:** “현재 화면에 그려진 경로가 어떤 입력으로 계산된 것인지”를 앱이 기억할 수 있게 한다.
- **보관 항목(예시):**
  - 출발지 문자열(또는 계산 시 사용한 식별자)
  - 도착지 문자열(또는 계산 시 사용한 식별자)
  - 경유지 배열: 개수·순서·각 경유지 이름(또는 좌표 요약)
  - 이동 수단(mode)
- **보관 시점:** `calculateRoute`가 **성공적으로** 경로를 받아와 `route` state를 갱신한 직후. (Directions·Elevation 완료 후, setRoute 호출 직후.)
- **보관 위치:** state 또는 ref. “현재 경로가 현재 입력과 일치하는지” UI 표시가 필요하면 state, 단순 분기만 필요하면 ref도 가능.

### 3.2 “입력 일치 여부” 판단 기준

- **일치로 볼 조건(모두 만족 시):**
  - 출발지: 현재 입력(origin)과 마지막 경로 요청 시 사용한 출발지가 동일. (문자열 trim 후 비교, 또는 ref 사용 시 동일 좌표/객체 기준.)
  - 도착지: 위와 동일하게 destination 비교.
  - 경유지: 개수 동일, 순서 동일, 각 경유지 이름(또는 위치 식별) 동일.
  - 이동 수단: 현재 mode와 마지막 요청 시 mode 동일.
- **불일치 예시:** 사용자가 경로탐색 후 출발/도착/경유지 텍스트를 수정했거나, 경유지를 추가/삭제했거나, 이동 수단을 바꾼 경우. 이때는 Go 클릭 시 **재계산**해야 함.

### 3.3 Go 버튼 클릭 시 분기 로직

- **1단계:** 현재 `route`가 null이 아닌지 확인.
- **2단계:** “마지막 경로 요청 파라미터”와 “현재 입력(origin, destination, waypoints, mode)”이 위 3.2 기준으로 **일치**하는지 확인.
- **3단계 분기:**
  - **일치하고 route 존재:** Directions·Elevation 등 **경로 관련 API 호출 없이**, 이미 있는 `route`로 **시뮬레이션만 시작**하는 경로로 진입.
  - **불일치 또는 route 없음:** 기존과 동일하게 `calculateRoute(mode, true)`를 호출하여 경로 계산 후 자동 시작.

### 3.4 “시뮬레이션만 시작” 경로에서 수행할 작업

- **하지 않을 것:** Directions API, Elevation API, OSRM 호출, 새 polyline/경로 그리기(이미 그려져 있음).
- **할 것:**
  - 시뮬레이션 상태 초기화(현재 인덱스 0, 재생 상태 등).
  - 앱 단계를 PREPARING으로 전환(이미 있는 `route.panoData`·`cachedCoaching` 등 활용 가능한 부분은 그대로 두고, 필요 시 pre-fetch만 보완).
  - 주행 시작 브리핑(getCourseBriefing) 재생 등 기존 “시작 시” 로직 수행.
  - PREPARING 완료 후 RUNNING 전환.

즉, **경로 계산·setRoute** 부분만 건너뛰고, **“경로가 이미 있을 때 재생 버튼을 눌렀을 때”**와 유사한 “시작 처리”만 수행한다고 보면 됨.

### 3.5 엣지 케이스 정리

| 상황 | 처리 |
|------|------|
| 한 번도 경로탐색/경로 계산을 하지 않음 | route 없음 → Go 클릭 시 기존처럼 전체 계산 후 시작. |
| 경로탐색 실패(에러)로 route가 null | route 없음 → Go 클릭 시 전체 계산. |
| 경로탐색 성공 후 사용자가 출발/도착/경유지/모드 중 하나라도 수정 | 입력 불일치 → Go 클릭 시 재계산 후 시작. |
| 경로탐색 → Go (입력 수정 없음) | 입력 일치 + route 존재 → 재계산 없이 시뮬레이션만 시작. |
| 즐겨찾기에서 경로 불러온 뒤 경로탐색 → Go | 불러온 값으로 경로탐색한 결과와 현재 입력 일치 → 재계산 없이 시작 가능. |
| 즐겨찾기 불러온 뒤 바로 Go (경로탐색 안 함) | 아직 route가 이번 입력으로 계산된 적 없을 수 있음 → route가 없거나 “마지막 요청”이 불러온 입력과 다르면 재계산. |

### 3.6 “마지막 경로 요청” 초기화 시점

- **저장:** 경로 계산이 **성공적으로** 끝나서 setRoute가 호출된 직후.
- **초기화(비우기):** 사용자가 “경로 삭제”(clearMapOverlays 등)를 수행했을 때, 또는 출발/도착을 비워 경로를 무효화했을 때. 이때는 “마지막 요청”도 함께 비워 두어, 다음 Go 클릭 시 무조건 재계산하도록 함.

---

## 4. 기대 효과

- **경로탐색 → Go** 시나리오에서 Directions·Elevation 호출 **1회 제거** → 서버 트래픽·비용 감소.
- 동일 입력에 대한 중복 계산 제거로 **응답 속도** 개선(Go 클릭 후 즉시 PREPARING/시작 처리).
- 사용자 관점에서 “이미 본 경로로 바로 출발”하는 동작이 명확해짐.

---

## 5. 구현 시 유의사항 (요약)

1. **일치 판단:** 문자열 비교 시 공백·대소문자 등 팀 정책에 맞게 통일(예: trim, 정규화).
2. **경유지:** 이름만으로 비교할지, 좌표가 있으면 좌표까지 포함할지 정책 결정. 이름+개수+순서만으로도 실무상 충분한 경우 많음.
3. **ref(originLocationRef/destLocationRef):** 지도 클릭 등으로 ref만 바뀌고 문자열은 같은 경우, “동일 입력”으로 볼지 여부를 정책으로 정함. 보수적으로 하려면 “마지막 계산 시 사용한 origin/destination 문자열”을 그대로 저장해 두고, 현재 입력 문자열과만 비교하는 방식이 단순하고 안전함.
4. **startSimulationOnly(또는 유사 함수)** 를 새로 두고, “경로는 그대로, 시뮬레이션만 시작” 로직을 한곳에 모으면, Go 분기와 나중에 “일시정지 후 재개” 등과의 일관성 유지에 유리함.
