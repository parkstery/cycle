## Phase 1: 원칙 1·3 확정 — 주행 중 API 제거, 캐시 없으면 끄기

**목표**: 주행 중 Street View 관련 getPanorama 호출 0회. 캐시에 없으면 거리뷰 끄기 또는 “이 구간 거리뷰 없음” 표시.

### 1.1 작업 항목

| 번호 | 작업 | 상세 | 담당 코드 위치 |
|------|------|------|----------------|
| 1.1.1 | 주행 중 실시간 거리뷰 검색 블록 제거 | `route.panoData`가 없거나 현재 인덱스에 해당 pano가 없을 때, `findStreetViewInDirection` / `findStreetView` / `setPanoramaView` 호출하는 **else if (svServiceRef.current && !isSvSearching.current)** 블록 전체 제거 또는 비활성화. | App.tsx, 시뮬레이션 useEffect 내 STREET VIEW 섹션 (대략 848~900행 근처) |
| 1.1.2 | 캐시 미존재 시 동작 정의 | `getPanoDataForIndex` 결과가 null이거나, 해당 pathIndex 구간에 panoData가 없으면: (A) 현재 파노라마 유지하지 않고 **거리뷰 영역 숨김** 또는 (B) **“이 구간 거리뷰 없음”** 배지만 표시하고 파노는 이전 프레임 유지. 정책에 따라 (A) 또는 (B) 선택. | 동일 useEffect, route.panoData?.length 분기 내부 |
| 1.1.3 | 슬라이딩 prefetch는 유지 | “캐시 끝 근처에서 다음 구간 prefetch”는 **주행 중 API = 0**을 깨지 않음(prefetch는 경로 확정 후·백그라운드). 현재 로직 유지하되, Phase 3에서 구간 길이만 확대. | isSegmentFetchingRef, preFetchStreetViewData 호출부 |
| 1.1.4 | 상수·주석 정리 | “주행 중에는 캐시만 사용, 실시간 검색 없음” 원칙을 주석으로 명시. `MAX_REALTIME_SV_ATTEMPTS` 등 실시간 전용 상수는 사용처 제거에 따라 삭제 또는 레거시 표시. | App.tsx 상단 상수, useEffect 주석 |

### 1.2 완료 기준

- [ ] 주행 중 `getPanorama`(또는 `getPanoramaWithFallback` / `findStreetView*`)가 **한 번도 호출되지 않음** (로그 또는 브레이크포인트로 검증).
- [ ] panoData가 비어 있거나 현재 위치에 항목이 없을 때, **거리뷰 끄기** 또는 **“이 구간 거리뷰 없음”** 안내가 노출됨.
- [ ] 슬라이딩 prefetch(다음 Nm 구간)는 동작하며, prefetch 완료 전까지는 해당 구간에서 위 “없음” 처리만 적용됨.

### 1.3 리스크·참고

- panoData가 전 구간을 커버하지 못하는 경로에서, **처음부터 거리뷰가 거의 안 나오는** 구간이 생길 수 있음. Phase 2·3에서 prefetch 품질을 올려 coverage를 높이는 것이 보완.

## Phase 2: Prefetch 후보 수집 + 점수 선택

**목표**: 단일 조건(통과/탈락) 제거. 여러 후보 수집 후 점수로 1개 선택해 panoData에 저장.

### 2.1 작업 항목

| 번호 | 작업 | 상세 | 담당 코드 위치 |
|------|------|------|----------------|
| 2.1.1 | Multi-pass 탐색 (2단계 단순화) | 시니어 의견 반영: 1단계 50m ±40°, 2단계 120m 제한 없음. 각 샘플 지점에서 (1) 50m·±40°로 후보 수집, (2) 없으면 120m·제한 없음으로 추가 수집. getPanoramaWithFallback 호출 시 **여러 후보를 배열로 수집** (기존처럼 첫 성공 시 break 하지 않음). | preFetchStreetViewData 내부, findStreetViewInDirection / findStreetView 호출 루프 |
| 2.1.2 | 후보 메타데이터 보관 | 각 후보에 대해: pathIndex, panoId, location(또는 lat/lng), heading, 거리 d, 방향 차이 diff, isUserPhoto(usedFallback). (실내 필터용 tilt 등은 Phase 4에서 추가.) | preFetchStreetViewData, PanoDataItem 확장 또는 로컬 후보 타입 |
| 2.1.3 | 점수 함수 도입 | score = 0.6×(1 - d/maxD) + 0.4×(1 - diff/90). maxD = 현재 단계 반경(50 또는 120). diff = 주행 방향과 pano 방향 차이(절대값, 도). 후보가 0개면 null, 1개 이상이면 **최대 점수 1개**만 선택. | preFetchStreetViewData 내부, 후보 배열 처리 |
| 2.1.4 | 저장 형식 유지 | 선택된 1개만 기존 PanoDataItem 형태로 panoData에 push. 기존 { pathIndex, panoId, location, heading, isUserPhoto } 유지. | panoData.push(item) 부분 |

### 2.2 완료 기준

- [ ] prefetch 시 샘플 지점당 **후보가 2개 이상일 때** 점수가 높은 1개만 저장됨.
- [ ] 50m ±40°에서 후보가 없으면 120m 제한 없음 단계가 실행됨.
- [ ] 주행 중 로직은 Phase 1과 동일하게 **캐시 lookup만** 사용하며, 동작 변화 없음(표시 품질만 개선).

### 2.3 조정 사항

- 가중치(0.6/0.4), maxD, diff 분모(90)는 **실제 경로 2~3개**로 테스트 후 필요 시 상수화하여 조정.

## Phase 3: densifiedPath 완화 + prefetch 구간 확대

**목표**: 호출 수 감소(2m→10m) + 끊김 감소(초기 300m, 슬라이딩 400m).

### 3.1 작업 항목

| 번호 | 작업 | 상세 | 담당 코드 위치 |
|------|------|------|----------------|
| 3.1.1 | segmentLength 2 → 10 | 경로 보간 시 segmentLength = 10 (단위: m). densifiedPath 생성 루프에서 stepCount·computeOffset 간격을 10m로 변경. | App.tsx, calculateRoute 내 densifiedPath 생성 (segmentLength = 2 부근) |
| 3.1.2 | prefetch 샘플 간격(intervalM) 정합 | 현재 7m. densifiedPath가 10m 간격이면 intervalM을 10으로 통일해도 됨. (7 유지 시 10m path 위에서 7m 간격으로 샘플링.) 팀 선택: 10m로 통일 권장. | preFetchStreetViewData options, 호출부 intervalM |
| 3.1.3 | 초기 prefetch 구간 200m → 300m | 경로 생성 직후 preFetchStreetViewData 호출 시 maxDistanceM: 200 → 300. | calculateRoute 내 preFetchStreetViewData(..., { maxDistanceM: 200, ... }) |
| 3.1.4 | 슬라이딩 구간 200m → 400m | “캐시 끝 근처에서 다음 구간” 요청 시, fromM ~ toM 범위를 **다음 400m**로 확대. 현재 (distAtLast+10, distAtLast+200) → (distAtLast+10, distAtLast+400) 또는 (distAtLast+50, distAtLast+450) 등으로 조정. | 시뮬레이션 useEffect 내 fromM, toM 계산 |
| 3.1.5 | 슬라이딩 트리거 거리 | “남은 거리 < 200m일 때 다음 prefetch” 유지. 필요 시 250m로 완화해 조기 트리거 가능. | currentIdx >= lastPano.pathIndex - 150 근처 조건 |

### 3.2 완료 기준

- [ ] densifiedPath 점 개수가 기존(2m) 대비 약 1/5 수준으로 감소.
- [ ] prefetch 호출 횟수(샘플 수)가 동일 구간 기준으로 감소.
- [ ] 초기 300m + 슬라이딩 400m 적용 시, 주행 중 “거리뷰 없음” 구간이 눈에 띄게 줄어듦(체감 테스트).
- [ ] 10m 보간으로 인한 **화면 전환 주기**가 수용 가능한지 짧은 구간으로 확인.

### 3.3 리스크·참고

- 10m에서 전환이 너무 굵게 느껴지면 7m로 되돌리거나, segmentLength만 10m로 두고 intervalM은 7m 유지하는 절충 가능.

## Phase 4: 실내 파노 필터 (tilt, 가능 시 메타데이터)

**목표**: 실내/상가 등 부적합 파노를 후보 단계에서 제외. tilt 우선, API 제공 범위 내에서 메타데이터 보조.

### 4.1 작업 항목

| 번호 | 작업 | 상세 | 담당 코드 위치 |
|------|------|------|----------------|
| 4.1.1 | getPanorama 응답 필드 확인 | Google Street View API(getPanorama) 콜백에서 반환되는 객체에 **tilt**, **description**, **copyright** 등이 있는지 문서·실제 응답 로그로 확인. | getPanoramaWithFallback 콜백, 또는 별도 유틸 |
| 4.1.2 | tilt 이상치 필터 | 응답에 tilt(또는 pitch)가 있으면, 임계값(예: 절대값 > 30° 또는 팀 정의값)이면 **후보에서 제외**. Phase 2 후보 수집 직후, 점수 계산 전에 적용. | preFetchStreetViewData, 후보 배열 필터 단계 |
| 4.1.3 | 메타데이터 키워드 필터 (선택) | description/copyright에 "Shop","Indoor","Business" 등이 포함되면 제외. API에서 제공하지 않으면 스킵. | 동일, 필터 단계 |
| 4.1.4 | 필터 후 선택 | 필터 통과한 후보만 남기고, Phase 2와 동일하게 **최대 점수 1개** 선택. | 기존 점수 선택 로직 |

### 4.2 완료 기준

- [ ] tilt(또는 pitch) 값이 있는 경우, 이상치 제외 시 실내처럼 기울어진 파노가 목록에서 빠짐.
- [ ] 메타데이터 필터는 API 제공 범위에 맞춰 적용 여부 결정됨.
- [ ] 필터로 인해 후보가 0개가 되면 해당 샘플은 panoData에 포함하지 않음(Phase 1에 따라 주행 시 “없음” 표시).

### 4.3 리스크·참고

- tilt 임계값은 샘플 구간으로 테스트 후 조정. 너무 공격적이면 정상 도로 파노가 빠질 수 있음.

## Phase 5: coverage 정책 + 사용자 안내

**목표**: prefetch 품질이 낮은 경로(coverage 70% 미만)에서는 Street View 비활성 또는 명시적 안내.

### 5.1 작업 항목

| 번호 | 작업 | 상세 | 담당 코드 위치 |
|------|------|------|----------------|
| 5.1.1 | coverage 계산 | prefetch 완료 후 coverage = (panoData 항목 수) / (샘플 수). 샘플 수는 preFetchStreetViewData 내부에서 이미 사용 중인 samples.length. | preFetchStreetViewData 반환 직후 또는 setRoute 직전 |
| 5.1.2 | 임계값 상수 | COVERAGE_MIN = 0.7 (70%). 팀 결정에 따라 조정 가능. | App.tsx 또는 types 상수 |
| 5.1.3 | coverage < 70% 시 동작 | (A) **Street View 비활성**: 해당 경로에 대해 거리뷰 버튼 비활성 또는 자동으로 isSvActive false 유지. (B) **안내만**: panoData는 저장하되, “이 구간은 거리뷰가 부족합니다” 배지 표시하고, 거리뷰는 켜두기. 정책 선택 후 구현. | calculateRoute 내 prefetch 완료 후 분기, 또는 route 저장 시 플래그 |
| 5.1.4 | 사용자 안내 문구 | “이 구간은 거리뷰가 부족합니다” (또는 팀 문구)를 UI에 노출. 기존 showSvWarning과 통합하거나 별도 상태. | 인포/배지 컴포넌트, 상태 |

### 5.2 완료 기준

- [ ] coverage가 70% 미만인 경로에서, 정책에 따라 비활성 또는 안내가 노출됨.
- [ ] 70% 이상인 경로는 기존처럼 거리뷰 사용 가능.

### 5.3 리스크·참고

- coverage 계산 시 “샘플 수”는 prefetch에 실제로 사용된 샘플 개수와 동일해야 함(intervalM·fromDistanceM·maxDistanceM에 의해 결정).

## 일정·의존 관계 제안

```
Phase 1 (원칙 1·3)     → 1~2일
       ↓
Phase 2 (후보+점수)   → 2~3일  ← Phase 4(실내 필터)는 2와 병렬 또는 직후
       ↓
Phase 3 (10m+구간확대) → 1~2일
       ↓
Phase 5 (coverage)    → 1일
```

- **Phase 1** 선행 필수: 이후 모든 단계가 “주행 중 API 0”을 전제로 함.
- **Phase 2** 완료 후 Phase 3(구간·간격) 적용 시, 호출 수·체감을 함께 검증하기 좋음.
- **Phase 4**는 API 스펙 확인이 필요하므로 Phase 2와 병렬로 스펙 조사 후, 후보 수집 파이프라인에 필터만 끼워 넣으면 됨.
